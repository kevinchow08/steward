# 端侧 AI 业务方向重新梳理（Week 3 后期）

背景：Week 3 想做的"文档动态分类"折腾了很多轮，反复验证下来，"把一堆文件自动整理成一个整洁、数量少的分类目录树"这个具体目标，用端侧小模型做不稳，而且跟前沿云端 agent（Cowork）对比后发现，连它也不是靠"判断更准"做到的，是靠绕开这个问题（读文件夹结构）做到的——说明这不只是端侧能力不够，是这个目标本身的形状可能就不太适合"一堆独立判断收敛成一个小体系"这条路。这份文档是借这个契机，把"端侧 AI 到底能稳定交付什么体验"重新梳理一遍，往上抬一层看整体业务方向，不是就事论事继续磨分类这一件事。

## 现状速览（新接手的 session 先看这一节）

**⚠️ 2026-09-07 更新，回头复查 8-31 那次地基审计记的 6 条"新发现"，逐条对照这周实际做的东西——5 条已修复并有真实数据验证，1 条部分修复：**

1. **文件生命周期管理/增量索引 —— 已修复**：统一支持多目录/多盘共享数据库（`target_dir`/`volume_label` 字段），`index`/`tag` 都支持增量（内容没变跳过）+ `--force`（强制全量重跑）。真实踩过并修掉两个具体 bug：`/tmp` 是 macOS 软链接导致路径前缀匹配静默失效（改用 `.resolve()`）、SQL `LIKE` 通配符转义（文件夹名带 `_`/`%` 会被误当通配符）。
2. **语义搜索暴力线性扫描 + 没有关键词检索 —— 部分修复**：稠密检索改成 numpy 批量矩阵乘法（不再是 Python 逐个循环算余弦相似度）；新增关键词检索（SQLite FTS5，trigram 分词 + bm25 排序）+ RRF 融合排序，真实语料验证过（"投资建议"能靠关键词精确命中，"工程师思维"能靠标签级信号弥补稠密检索的部分不足，两路证据都有）。**仍然不是真正的近似最近邻索引结构**（本质还是暴力扫描，只是常数因子小了很多），语料量级再涨一个数量级需要重新评估；**也仍然没有像打标签那样补一次正式验收集**——见下面新增的用例，供自己验证用。
3. **表格类内容切片丢表头 —— 已修复**：新增 `chunk_tabular_text()`，按工作表边界切块，每个 chunk 都带表头，不只是第一个 chunk，真实 xlsx 验证过（842/842 chunk 正确）。
4. **Week 3 资源监控空白 —— 已修复(内存/CPU)**：双进程监控（steward 自己 + llama-server 分开测，两边内存开销是独立的两笔账），真实全量跑验证过（steward 自身峰值内存 ~935MB，llama-server 峰值 ~13.5GB）。**GPU 算力这一路仍然没测**，是主动决定不测（不想要 sudo 输入密码的体验代价），不是遗漏——Apple Silicon 统一内存架构下，内存这块已经间接覆盖了大部分实际需要回答的问题。
5. **打标签管线崩溃安全性脆弱 —— 已修复**：去掉了无条件清空旧数据的 Step 0、去掉了误导性的嵌套事务包装（`with index.connection:` 不提供真正的整体回滚，已用最小复现例子验证过），改成 upsert 语义，中途崩溃不会比运行前更差。
6. **文本提取范围 —— 更牢了**：又修了 chunk 切分断词 bug（英文单词被从中间切断）、markdown 图片/链接噪声清理，以及本轮最大的一处新发现——**大文件/JSON 代表性抽样问题**：一份 118MB 的 JSON 聊天记录导出文件曾导致索引耗时 101 分钟、且打标签摘要完全不具代表性（只反映了文件最早 0.0025% 的内容）。定位到两个独立的根因（chunk 数量爆炸 + 打标签摘要抽取只读开头）后，最初的修法是给 JSON 数组单独做"按记录抽样"，但**用真实的 118MB 文件实测对比后，发现这个 JSON 专属预处理反而让最终覆盖面变差**（1151 条记录只覆盖 180 条/15.6%，不做预处理直接靠统一的 chunk 数量上限兜底反而能覆盖 362 条/31.5%）——所以最终改成对所有格式统一处理，不再有 JSON 专属分支。索引耗时从 101 分钟降到 546 秒，真实验证摘要现在能跨两年时间线均匀取样，不再卡在最早一条记录上。**PDF 里约 18-20% 没有可提取文字层（纯扫描/字体缺 ToUnicode 映射）这个缺口依然没解决**，需要 OCR，明确搁置。
7. **语义搜索容易"为了结果而给结果"、`--top-k` 截断掉看不见的其余结果 —— 已修复**：新增最低相关度门槛（`_MIN_DENSE_SCORE = 0.5`，稠密检索原始余弦相似度低于它直接不进结果）+ 标签作为第三路 RRF 信号（新增 `document_tags_fts`，文档整体标签也能参与检索，补上"主题分散在全篇、没集中在某个 chunk 里"这个盲区）。用 8 个真实查询词测过：6 条干净（`不动产登记`/`微服务`/`日本签证`/`财务凭证`/`报销发票`/`工程师思维`），1 条部分好（`收入证明`，头部对、尾部混进弱相关发票），**1 条真实翻车**（`银行流水`：稠密检索把一份 SQL migration 教程的原始相似度（0.545）排到很高，清过了 0.5 门槛——最初以为是"压过了一份真正相关的发票（0.4746）"，靠标签信号把那份发票捞了回来；但后续换 pymupdf 重新提取+重新打标签后发现，那份发票其实是普通餐饮发票，文本变干净后 LLM 不再给它"银行流水"标签，说明最初那个标签是读乱码文本时的不精确猜测——**语料里可能根本没有真正意义上的"银行流水"类文档，这份 SQL migration 教程的假阳性依然清过门槛被当成"找到了"**，性质上更接近"语料里没有相关内容却没被门槛正确拦住"，不是"假阳性压过真阳性"）。诊断出翻车的根因不是"专业词汇普遍不可靠"（`不动产登记` 同样生僻但结果完美），而是"流水"这个词本身有歧义（银行流水/流水线/流水号）容易把向量模型搞混，是个具体、可解释的个例，不是系统性问题。**这个 0.5 阈值明确记录为"当前证据支撑的估计值，跟具体 embedding 模型和语料内容分布绑定，不是通用常数"**，换模型或语料大幅变化需要重新用真实查询校准（曾尝试用"这次查询自己的分数距全库均值几个标准差"做动态阈值，实测效果不如绝对值，没有采用）。附带新增 `tags --tag <关键词>` 命令，补上"穷举式列出所有真正带这个标签的文档"这个能力缺口（`search` 是排序找最相关的几个，会被门槛/top-k 过滤，不保证完整；这个命令直接读 `document_tags_fts`，不加载 embedding 模型，用户自己验证过"基本很准"）。
8. **PDF 提取器从 pypdf 换成 pymupdf**：上面第 7 条测试时撞见几份发票 PDF 提取出来是乱码（泰米尔文/古吉拉特文这类跟文档内容毫不相关的字符），查了字体结构，根因是这批 PDF 用 Identity-H 编码的内嵌字体、ToUnicode 映射缺失或不完整，`pypdf` 解析失败后瞎猜出了乱码——**这跟"PDF 完全没有文字层，只能靠 OCR"是不同类型的问题**：那类是真没救（两个库测都是空的），这类是能修的，实测把提取器换成 `pymupdf` 之后同样文件能正确还原成汉字（字体处理更健壮，能从字体文件自己内部的映射表兜底），`报销相关` 目录下 64 份真实发票交叉测试没有发现回归。附带许可证考量：pymupdf 是 AGPL/商业双授权，现阶段本地个人工具不受影响，以后如果谈产品化分发，这是需要重新评估的一个点，不是可以忽略的细节。

**⚠️ 2026-08-27 更新，这是这份文档最新、最重要的一条结论，务必先看：分类体系（category/taxonomy）已经被完整废弃，代码库里不再维护任何分类。** 这几周从 V1（聚类打标签）到 V2（开集逐文件分类）再到 V3（taxonomy 归纳+闭集分类），每一版都花了大量精力打磨、每一版都能用真实数据证明"能力比上一版强"，但每一版最终都在新的真实文件上炸出新的边界案例——直到最后一轮复盘才定位到根因：**这不是哪次没调好参数，是"让每个文件收敛到唯一分类"这个目标本身，跟真实文件天然多归属、边界模糊的性质是冲突的**（比如一篇"用工程师思维聊投资"的文章，本来就该同时挂"投资""工程师思维"这两个标签，不该被逼着二选一）。完整的踩坑记录、三个独立根因（reasoning 生成截断、规则覆盖不检查原始判断、taxonomy 覆盖不到的内容会被强行硬凑）、每一条的真实证据，见 [docs/dynamic_classification_architecture.md](dynamic_classification_architecture.md) 的"最终结论"一节。

**现在的架构**：只保留两样东西——**tags**（开放式、多标签、不受固定列表限制，这几周所有压力测试里唯一没被真实数据打脸过的能力）和 **reasoning**（开放式一句话内容描述，不再是"为分类做依据"）。`categories` 表、`category_id` 字段、`Stage A/A-verify/B-override` 整套机制已经从代码里删除，不是标记废弃、是物理删除，见 `src/steward/semantic_classifier.py` 最新版本。`main.py tag` 命令的 `--structural-base-url`/`--structural-model` 参数也一并删除（是给 taxonomy 归纳这一步单独配大模型用的，这一步已经不存在了）。

后续"整理目录"这个目标不再指望分类体系兜底，改成"tags 聚类"——不在索引阶段强行归类，而是在用户想整理的那一刻现算一次分组建议（算错了重新点一次，不会像强制分类那样写死进数据库、层层传导）。具体聚类原则、以及顺带识别出的几个风险更低的真刚需方向（重复文件检测、安装包清理建议、文档摘要、通用文件名重命名建议），也记在 `dynamic_classification_architecture.md` 的"最终结论"一节里。

以下是这几天更早之前的实际进展，跟下面"一、地基审计"表格里当初写的"待办项"相比，这几条已经从"没做/没测过"变成"做完并验证过"（**注意**：下面这几条里提到"分类""category"的地方，按今天的最终结论已经不存在了，只保留 tags/reasoning 部分仍然成立）：

- **打标签质量验收：已通过。** 按下面"二、打标签验收"定义的参考案例集实测跑过，**零跨类别污染**（唯一硬红线）全部守住，标签具体、相关，人工抽查结果符合预期。当时表格里"打标签质量：需要一份明确的验收标准"这一行，现在已经是**过去式**。
- **非文档类型文件的覆盖缺口：已修复。** 原来 `indexing.py` 只给"支持内容提取"的文件（pdf/docx/txt/md/html）调用 `upsert_document()` 写入数据库，图片/视频/代码/压缩包这类文件完全没有进数据库，是"安静地遗漏"。现在改成扫描到的每个文件都先登记 `documents` 表（带 Week 1 判断出的 `basic_type`），只有提取/分段/向量化这部分才按是否支持格式跳过。同时 `semantic_classifier.py` 新增了一个轻量的"基础类型识别"档位（不读内容、不过 SLM，直接用 `basic_type` 生成 `category`/`tags`），让这些文件也能出现在 `tags` 报告里，标注为"基础类型识别"而不是伪装成语义打标签。真实语料（`~/Downloads` 618 个文件）验证过：全部 618 个文件都进了库，其中 77 份走了深度打标签，538 份走了基础类型识别，3 份未归类。

- **架构从"聚类后打标签"（V1）彻底转向"逐文件独立打标签"（V2）**：V1 遗留的 `semantic_clusters` 表、`documents.cluster_id` 字段/外键、`save_semantic_cluster()` 方法已经从 schema 里整个删掉（不需要迁移，因为 `steward.db` 本来就不进版本控制，重新跑一次 `index` 就是干净状态）。

## 一、地基审计（截至 Week 3 后期，如实写，不护短）

**重新定位**：分类结果（category）不直接展示给用户，只作为后续行为/检索的内部参考信号——这意味着"归一化后有多少个分类名"从验收红线降级成了次要指标，真正的红线只有一条：**内容判断不能串味**（不相关内容不能被塞进同一类/同一堆标签）。这条红线目前验证下来是守住的。

| 地基 | 状态 | 说明 |

## 二、打标签验收：参考案例回归集（本轮优先做这个）

把今天验证用过的真实案例固定成一份可以反复重跑的小型回归集，不再靠肉眼重新扫报告判断"这次是不是比上次好"：

- **案例池**：简历 ×3、AI 聊天记录 ×5（音乐/投资/技术/旅行等不同话题）、发票 ×2、证件材料 ×1，后续可以再扩。
- **通过标准（按优先级）**：
  1. 零跨类别污染——不相关内容不能被塞进同一类/同一批高分标签，这条是唯一的硬红线。
  2. 每个案例的分类结果，人工看一眼认为合理，不要求措辞完美。
  3. 每个案例排名靠前的标签里，看不到明显不相关的词。
  4. 分类名数量不再是硬指标，只要求不随文件量线性暴涨。
- 以后改动分类/打标签逻辑，就拿这份集合重新跑一遍对照这四条，而不是重新肉眼扫全量报告。

**语义搜索和标签质量都建议照这个方法补一次验收**——挑几个已知"应该搜得到"的真实案例，定义"排在前几名才算过"，现在完全没做过。

## 三、打标签对语义搜索有没有帮助

有，但不是直接替代关系，是两件事：
1. **标签可以作为搜索的一个独立信号**，跟向量相似度搭配用（比如查询词直接命中某个标签，可以在排序时额外加权）——这是常见的"稠密向量+关键词/标签"混合检索思路，标签质量好，这条路才走得通。
2. **标签服务的是"浏览"，搜索服务的是"提问"**，是两种互补的交互方式，不是谁替代谁。
3. 但两者共享同一套底层（文档向量+embedding 模型），验证标签质量能**部分**建立对搜索质量的信心（至少证明向量空间本身是可用的），不能完全替代——搜索还有自己独有的环节（query 向量化、chunk 级排序），需要单独测。

**结论**：能稳定对外交付体验的，是"找得到"（搜索）和"认得出、能筛选"（打标签），不是"自动摆放整齐"（分类目录）。这不是能力不够，是要交付的东西选错了形状。

## 二、Week 3 目标与交互形态：建议怎么调

### 从"分类"改成"打标签"，不只是换个词

"分类"这个词本身在暗示"每个文件归到一个确定的位置"——一旦文件被放错，用户体验是"AI 出错了、不可用"，容忍度很低。"打标签"暗示的是"辅助信息，允许不是每个都 100% 精确，用来筛选/搜索足够用"——同样的底层准确率，用户对"某个标签不太贴切"的容忍度，远高于对"文件被塞进错误文件夹"的容忍度。今天一整天验证出来的东西，恰好直接支持这个产品化结论：不是我们的判断变差了，是"分类"这个交互形态对错误零容忍，"标签+搜索"这个形态天然更宽容。

### 建议的 CLI 形态

```
steward index <目录>        # 建索引（已有）
steward search <query>      # 语义搜索（已有）
steward tag <目录>          # 原 classify，建议改名并调整对外描述：产出多标签，不强调"分到一个类"
steward duplicates <目录>   # 新增：重复/相似文件检测
```

`tag` 命令的输出（2026-08-27 更新）不再带"主分类"字段——这条当时是预判，后来真实做了几周验证，发现"主分类"这个概念本身就是问题所在，不只是"该不该主推"的问题，已经被完整移除，见上面"现状速览"。对外展示/宣传主推的是"打了哪些标签、能不能搜到"，这条判断被后续的真实数据完整印证了。

## 三、端侧 AI 业务亮点 brainstorm（结合公司 toC 存储产品定位）

公司做 toC 存储产品，用户的数据文件本来就活在盘/本地目录里——这个前提本身就是端侧 AI 最自然的战场，不需要说服用户"把数据交给端侧处理"，数据已经在那了。按用户能直接感知到的价值分成四组：

### A. 找得到（Find）
- **端侧语义搜索/问答**：已有，文本文档场景成立。以后如果接一个轻量的图文联合 embedding 模型，同一套向量检索基础设施可以直接复用到图片语义搜索（"去年夏天在海边拍的照片"），不需要重新设计架构。

### B. 认得出（Recognize / Tag）
- **文档多标签**：已验证。
- **图片语义标签**（人物/风景/文档扫描/截图/宠物/美食……）：存储设备的典型用户手里有大量照片视频，"识别照片内容、按人物/地点/事物搜索"是几乎所有云相册产品的核心卖点（Google 相册、iCloud 相册），但那些都是上传云端处理的。**端侧版本是真正的差异化**：不用上传就能搜，而照片视频恰好是用户最不愿意上传云端的数据类型之一——隐私是硬卖点，不是营销话术。

### C. 清得爽（Clean / Optimize）
- **重复/相似文件检测**：技术门槛低（图片用感知哈希、文档用已有向量相似度），可以直接续着现有代码做，不依赖今天纠结的分类收敛问题。直接呼应存储产品的核心价值——"你的硬盘里有 3.2GB 重复照片"是很有说服力的演示效果，而且是"省空间"这个存储公司天然在乎的叙事。
- **闲置大文件/安装包识别**：同样低门槛，同样贴合"存储优化"这个产品定位。

### D. 保得住（Protect / Backup Awareness）
- **敏感文件识别与保护提醒**：检测身份证、合同这类敏感文件是不是明文存放，提示要不要加密/隔离。端侧处理这类数据用户完全没有心理负担，云端做这个用户会本能抵触；直接呼应"数据在你自己的设备上，安全由你自己的设备负责"这个存储硬件公司最核心的品牌叙事。
- **重要文件缺备份提醒**：某类文件（证件、合同）只有一份、没有第二个副本时主动提醒。这是需要**持续常驻监控本地设备**的场景——云端 agent 没有持续访问用户本地多块物理盘的能力，也没有动机去做这件事，这是结构性地做不到，不是暂时做得不够好。

### E. 跨盘协同（Cross-Drive）—— 最贴合公司业务模式、云端完全替代不了的方向
- **多盘/多设备去重与归档建议**（"这块新盘里的照片，一半已经在老盘备份过了，要不要清理"）。用户买多个存储设备（NAS + 移动硬盘 + U盘）本来就是这类公司的核心商业模式，端侧 AI 天然适合做"看看我这几块盘上都有什么、重不重复、该怎么归档"——**这是云端 agent 结构性做不到的**（它没法同时挂载访问用户的多块物理设备），是这几组里最值得重点标出来讲给领导听的方向，因为它不是"我们比云端做得好一点"，是"这件事本来就只有端侧能做"。

---

## 四、为什么要往这几个方向走，不是继续死磕分类

云端 agent 的优势：模型能力强、算力不受限、能做开放式的复杂推理和多步骤操作。它的天然弱点：处理隐私敏感内容有用户心理门槛（照片/证件/财务文件用户本能不想上传）、没法持续常驻监控本地多台设备、每次调用都有真实的算力和网络成本。

端侧的优势正好卡在它的弱点上：本地隐私敏感数据、持续后台监控、零上传门槛、离线可用。业务亮点应该往"云端做不了、或者用户不愿意让云端做"的方向找，不是往"云端本来就做得比我们好"的方向死磕——今天在"自动整理成一个整洁分类目录"这件事上撞的墙，恰好就是一个云端更擅长的方向（它靠强大的通用推理能力硬啃，端侧硬啃不动），继续磨这个方向性价比很低。

---

## 五、这一轮"打地基探路"建议交付什么

给产品/领导看的，不需要现在做全，建议按"验证过的 vs 值得写进方向"分两层：

**现在就能包装成 CLI 演示的**（技术已经在手上，最多再加一个 `duplicates` 命令）：
- 语义搜索（已有）
- 文档打标签（已有，建议调整对外措辞）
- 文档去重检测（新增，技术门槛低）

**值得作为"下一步方向"讲清楚、但不需要这轮就实现的**：
- 图片语义标签与搜索（需要接入轻量视觉模型）
- 敏感文件保护提醒、备份完整性检测（需要设计"持续监控"的运行模式，跟现在"手动跑一次命令"的交互形态不一样）
- 多盘协同（需要设计跨设备的数据模型，是这几个方向里最有公司特色、但也是架构改动最大的一个，适合放在"愿景"那页 PPT，不适合放在这轮 CLI 验证范围内）
