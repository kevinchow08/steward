## 幂等性（Idempotency）

**同一个操作重复执行多次，结果都一样，不会因为多跑了几次就出错或者产生副作用。**

项目里的实际例子：
- `upsert_document()` 用 `ON CONFLICT(path) DO UPDATE`——同一个文件路径不管 upsert 多少次，最终状态都一样，不会因为重复调用就产生重复记录。
- `save_tagging_result()` 对标签列表用"先删除这个文档的旧标签、再插入新标签"，而不是简单地往表里 append——不这么做的话，同一个文档被重新打标签两次，标签会累积重复。
- 增量索引那次做的"内容没变就跳过重新处理"，本质也是在利用幂等性：因为重复处理是幂等的（结果一样），所以可以放心跳过没必要的重复。

## 竞态条件（Race Condition）

**两个（或更多）操作同时访问同一份共享状态，最终结果取决于谁先谁后执行到哪一步——顺序不确定，结果就不确定。**

真实踩过的例子（这次 session 里）：不小心同时跑了两个 `index` 进程、都写向同一个 SQLite 文件，其中一个进程执行到一半时另一个进程把数据库文件删了，直接报错——这就是一次真实的竞态条件事故，不是猜测出来的概念。

## 进程间通信（IPC）与"服务"的本质

进程和进程之间没法直接调用对方内存里的函数，必须靠某种通道交换数据：管道（pipe）、共享内存、或者最常见的——socket（HTTP/WebSocket 本质上都是包了一层协议的 socket 通信）。

聊到的场景：桌面应用（Electron/Tauri 的主进程，Node.js 或 Rust）要用现在这套 Python 代码的能力，不是直接调用，是把 Python 打包成一个独立子进程，主进程通过本地 HTTP 服务（或者 stdin/stdout 管道）跟它对话——这就是 IPC 的一个具体应用。

## 什么时候需要起一个"服务"（而不是跑一次退出的脚本）

两个独立的理由，任一成立就该考虑：
1. **需要监听、响应不由人手动触发的事件**——文件变化、插盘、定时任务、UI 请求。从服务自己的代码视角看，这些都是"一直 block 着等一个事件，事件来了就执行对应逻辑"，本质是同一种结构。
2. **摊销重复的启动开销**——比如 embedding 模型每次冷启动都要重新加载，常驻内存能省掉这个反复付出的成本，这条独立于"要不要监听事件"成立。

## SQLite vs 服务端数据库（MySQL/Postgres）的本质区别

不是单纯"有没有并发"，是**数据要不要被多个独立进程（尤其是可能在不同机器上）同时高强度访问**：
- SQLite 是嵌入式库，直接跑在调用它的应用进程里，天生服务"一个应用管自己本机的数据"这个场景，扛得住多个进程"轮流"访问，扛不住"很多进程同时高强度写"。
- MySQL/Postgres 是独立进程，天生要解决"进程外、多方同时访问同一份远程数据"，并发控制能力（连接池、行级锁、MVCC）是这个架构形态带来的必然要求，不是加出来的可选功能。

## 倒排索引（Inverted Index）—— 详细一点，因为这块之前理解模糊，值得多花点篇幅

### 解决什么问题：正排索引 vs 倒排索引

假设有 3 份文档：

```
doc1: "苹果手机很好用"
doc2: "苹果电脑价格贵"
doc3: "香蕉苹果都是水果"
```

**正排索引**是最自然的存法——"每份文档有什么内容"：
```
doc1 -> "苹果手机很好用"
doc2 -> "苹果电脑价格贵"
doc3 -> "香蕉苹果都是水果"
```
这份存法回答"doc1 里有什么"很快，但回答"哪些文档提到了苹果"很慢——**必须把 3 份文档全部读一遍，逐个检查**，文档数量一大，这个检查次数跟着线性增长。这正是这次会话里最开始的 `_dense_search()` 在做的事（对每个 chunk 向量算一次相似度），只是换成了向量而不是关键词。

**倒排索引**把这个对应关系反过来存——"每个词，出现在哪些文档里"：
```
"苹果" -> [doc1, doc2, doc3]
"手机" -> [doc1]
"电脑" -> [doc2]
"香蕉" -> [doc3]
"水果" -> [doc3]
```
这样一来，"哪些文档提到了苹果"直接查 `"苹果"` 这一行就有答案，不需要把 3 份文档重新读一遍——**用建索引时多做的一次性工作，换查询时的速度**，这是空间换时间的典型例子。每个词对应的那一串文档编号，专业说法叫 **posting list（倒排列表）**。

### 项目里怎么落地的：`chunks_fts` 这张表，本质就是一个倒排索引，只是 SQLite 帮你管理了

[document_index.py](../src/steward/document_index.py) 里这句：
```sql
CREATE VIRTUAL TABLE IF NOT EXISTS chunks_fts USING fts5(text, tokenize='trigram')
```
`FTS5`（Full-Text Search 的第 5 代实现）是 SQLite 自带的倒排索引引擎——建这张"虚拟表"的时候，SQLite 在背后真正建的不是一张表，是好几张：

```
chunks_fts          <- 你写 SQL 时用的这个名字，只是个外壳
chunks_fts_data      <- 真正的倒排索引数据本体（posting list），压缩过的二进制格式
chunks_fts_idx       <- 索引的 b-tree 结构，加速定位到 chunks_fts_data 里的哪一块
chunks_fts_content   <- 原始文本内容（如果建表时选择自己存储原文，这里会有）
chunks_fts_docsize   <- 每一行(每个 chunk)的 token 数量，bm25 排序要用长度归一化
chunks_fts_config    <- FTS5 自身的配置项(比如版本号)
```
这些表是真实存在的（在你自己的 `steward.db` 里可以直接 `SELECT name FROM sqlite_master WHERE type='table' AND name LIKE 'chunks_fts%'` 查到），只是里面的数据大部分是 SQLite 自己定义的压缩二进制格式，不是能直接用 `SELECT *` 看懂的明文行——这也是为什么"感觉内部实现不清晰"：**不是没有实现，是它被故意封装成了黑盒，你只通过 `MATCH` 这个操作符跟它打交道，不需要（也没法直接）手动摆弄底层的 posting list**。这跟你自己写的 `documents`/`chunks` 这些普通表完全是两回事——那些每一行都是你自己定义的、完全透明的数据。

### trigram 分词具体切的是什么

英文天然按空格分词（"apple phone" 很自然地切成 "apple"、"phone" 两个词去建索引），中文没有空格，"苹果手机"整体是一串连续字符，SQLite 默认的分词器（`unicode61`）按空格切，对中文等于不分词，整句话被当成一个词，几乎没有实用价值。

`trigram` 分词器不管语言，不找词的边界，**固定切"连续 3 个字符"的滑动窗口**：
```
"苹果手机" (4 个字符) 切出来的 trigram:
位置 [0:3] = "苹果手"
位置 [1:4] = "果手机"
```
每个 3 字符片段都单独建一条倒排索引记录。这就是为什么查询至少要 3 个字符才能命中任何东西——查 `"苹果"`（2 个字符）在索引里根本找不到对应的 trigram（索引里存的都是 3 字符的片段），查 `"苹果手"`（3 个字符）能直接对上第一条。这次会话里实测过 `"投资"`(2字) 查不到、`"投资建议"`(4字，内部会被切成 `"投资建"`、`"资建议"` 两个 trigram，用 AND 逻辑同时满足) 能查到，就是这个机制的直接体现。

### bm25 排序，是在倒排索引之上做的事，不是倒排索引本身

倒排索引负责回答"哪些文档命中了"，**bm25 负责回答"命中的这些里，哪个排前面"**——一个词在某份文档里出现得越频繁、但这个词在整个语料库里又不算常见（比如"苹果"到处都是，区分度低；"雷克沙"这种专有名词很少见，区分度高），这份文档的 bm25 分数就越高。这次会话里验证过 bm25 是"数值越小越相关"（反直觉的一点，跟大多数"分数越高越好"的直觉反着来），SQLite 的 `bm25()` 函数就是直接对着 `chunks_fts_docsize`（每行的 token 数量）和倒排索引本身的统计信息算出来的。
