# 学习笔记（轻量记录，主线任务空出来的时候自己再深挖）

这份文档不是项目状态记录，是这次做 steward 过程中聊到的、值得往"通用工程概念"上抽一层的东西。
每条只记"叫什么、在这个项目里对应哪个具体场景"，不展开讲，方便以后自己查资料时有个起点。

## 幂等性（Idempotency）

**同一个操作重复执行多次，结果都一样，不会因为多跑了几次就出错或者产生副作用。**

项目里的实际例子：
- `upsert_document()` 用 `ON CONFLICT(path) DO UPDATE`——同一个文件路径不管 upsert 多少次，最终状态都一样，不会因为重复调用就产生重复记录。
- `save_tagging_result()` 对标签列表用"先删除这个文档的旧标签、再插入新标签"，而不是简单地往表里 append——不这么做的话，同一个文档被重新打标签两次，标签会累积重复。
- 增量索引那次做的"内容没变就跳过重新处理"，本质也是在利用幂等性：因为重复处理是幂等的（结果一样），所以可以放心跳过没必要的重复。

## 竞态条件（Race Condition）

**两个（或更多）操作同时访问同一份共享状态，最终结果取决于谁先谁后执行到哪一步——顺序不确定，结果就不确定。**

真实踩过的例子（这次 session 里）：不小心同时跑了两个 `index` 进程、都写向同一个 SQLite 文件，其中一个进程执行到一半时另一个进程把数据库文件删了，直接报错——这就是一次真实的竞态条件事故，不是猜测出来的概念。

## 进程间通信（IPC）与"服务"的本质

进程和进程之间没法直接调用对方内存里的函数，必须靠某种通道交换数据：管道（pipe）、共享内存、或者最常见的——socket（HTTP/WebSocket 本质上都是包了一层协议的 socket 通信）。

聊到的场景：桌面应用（Electron/Tauri 的主进程，Node.js 或 Rust）要用现在这套 Python 代码的能力，不是直接调用，是把 Python 打包成一个独立子进程，主进程通过本地 HTTP 服务（或者 stdin/stdout 管道）跟它对话——这就是 IPC 的一个具体应用。

## 什么时候需要起一个"服务"（而不是跑一次退出的脚本）

两个独立的理由，任一成立就该考虑：
1. **需要监听、响应不由人手动触发的事件**——文件变化、插盘、定时任务、UI 请求。从服务自己的代码视角看，这些都是"一直 block 着等一个事件，事件来了就执行对应逻辑"，本质是同一种结构。
2. **摊销重复的启动开销**——比如 embedding 模型每次冷启动都要重新加载，常驻内存能省掉这个反复付出的成本，这条独立于"要不要监听事件"成立。

## 程序是怎么跑起来的——"从敲命令到服务响应"的骨架（2026-09-29）

这一块横跨三个领域的交界：操作系统基础、语言运行时（编译原理入门）、后端部署运维。学习目标不是背细节，是有一副骨架：以后遇到部署/进程/服务方面的问题，能靠骨架推断哪一层出了问题，而不是照抄操作。延伸阅读：《深入理解计算机系统》(CS:APP) 第 7、8 章；免费在线书 *Operating Systems: Three Easy Pieces*（OSTEP）。

### 谁在执行程序：内核，不是 shell / launchd / systemd

- **真正执行程序的永远是内核**：某个程序向内核发起系统调用（`fork` + `exec`），内核把二进制装进内存，让 CPU 开始跑。
- zsh、launchd、systemd 都只是"向内核申请启动程序"的普通程序。launchd（macOS）/systemd（Linux）是内核拉起的 1 号进程，负责开机自启、崩溃重启、日志，不负责执行。终端里敲 `python xxx.py` 走的是 zsh，跟 launchd 无关。
- 内核不知道什么叫"服务"，"常驻"是程序自己的无限循环造成的。验证：`ps -p 1 -o pid,comm`。
- 项目场景：steward 以后要常驻，交给 launchd 管，plist 里写的是 python 路径 + 参数。

### 编译型 / 解释型 / 字节码 + 虚拟机 / 运行时

- CPU 只认机器码，所有语言最终都要变成机器码，区别只是"谁、什么时候翻译"：Go/Rust 提前编成机器码，单文件自带一切；Python 由解释器（本身是二进制）读脚本、编成字节码、逐条执行；Java 先 `javac` 编成字节码，再由 JVM 加载并对热点代码 JIT；JS 由 V8 运行时 JIT。
- **运行时 = 引擎 + 配套能力**：JS 语言本身不能读文件、开端口，这些是运行环境给的。Node = V8 + fs/http；浏览器 = V8 + DOM/fetch。所以 vite 跑在 Node 上，Vue/React 跑在浏览器里。
- 项目场景：steward 是 Python，分发时用户机器上要有解释器，这就是 `build/`、`dist/`、pip 分发要解决的问题；Go/Rust 单文件没有这个问题。

### 一次性程序 vs 常驻服务

- 启动机制完全一样（都是 exec 出来的进程），区别只是代码里有没有永不结束的等待循环。判断问句："被叫到才做一次" vs "要一直等某个事件"。
- 项目场景：`index`/`tag`/`search` 是一次性程序；以后的本地 web 面板是常驻服务。

### Web 服务器、框架、语言运行时——三个角色别混

| | 运行时 | 服务器 | 框架 |
|---|---|---|---|
| Python | CPython | uvicorn（ASGI） | FastAPI |
| Java | JVM | 内嵌 Tomcat | Spring Boot |
| Node | node(V8) | 自带 http 模块 | Express / Nest |

- FastAPI 自己跑不起来，只是一个库；uvicorn 负责监听端口、收发字节，把请求交给框架路由到你的函数。全部在同一个进程里。
- `fastapi dev` = uvicorn + 热重载；`fastapi run` 是生产模式。Spring Boot 对应 `./mvnw spring-boot:run` 或 `java -jar app.jar`。
- 已知的坑：`async def` 里做同步耗时操作会卡死整个事件循环（steward 以后把本地模型推理接进 web 服务时要注意）；容器里服务要监听 `0.0.0.0`，只监听 `127.0.0.1` 外面访问不到。

### 前端构建 vs 运行

- vite/webpack 是跑在 Node 上的工具，只出现在开发/构建阶段：dev 命令起服务、资源放内存；build 命令生成 `dist` 后进程退出。上线后是 nginx 发静态文件，Vue/React 代码由浏览器执行，运行时不需要 Node。

### 容器（Docker）

- 镜像 = 文件系统快照 + 启动命令；容器 = 被内核隔离的普通进程，不是虚拟机。Linux 上链条是 systemd → dockerd → 容器进程。macOS 内核不是 Linux，Docker Desktop 会起一个轻量 Linux 虚拟机来跑 dockerd。

### PWA：把网页装成"像 app"的窗口

- 靠 `manifest.json`（名字、图标、`display: standalone`），`localhost` 免 HTTPS；Chrome 安装后在 `~/Applications` 生成 app shim，有独立 Dock 图标，但仍共用 Chrome 引擎，退出 Chrome 会连带关掉 PWA。Safari 的"添加到程序坞"不需要网站配合。Service Worker 是否是安装硬条件，资料说法不一致，真做时以 Chrome 官方文档为准。
- 项目场景：本地 web 面板的候选 UI 形态。深度系统集成（写 Spotlight 备注、后台常驻监控）PWA 做不到，需要时再评估 Tauri。

## SQLite vs 服务端数据库（MySQL/Postgres）的本质区别

不是单纯"有没有并发"，是**数据要不要被多个独立进程（尤其是可能在不同机器上）同时高强度访问**：
- SQLite 是嵌入式库，直接跑在调用它的应用进程里，天生服务"一个应用管自己本机的数据"这个场景，扛得住多个进程"轮流"访问，扛不住"很多进程同时高强度写"。
- MySQL/Postgres 是独立进程，天生要解决"进程外、多方同时访问同一份远程数据"，并发控制能力（连接池、行级锁、MVCC）是这个架构形态带来的必然要求，不是加出来的可选功能。

## 倒排索引（Inverted Index）—— 详细一点，因为这块之前理解模糊，值得多花点篇幅

### 解决什么问题：正排索引 vs 倒排索引

假设有 3 份文档：

```
doc1: "苹果手机很好用"
doc2: "苹果电脑价格贵"
doc3: "香蕉苹果都是水果"
```

**正排索引**是最自然的存法——"每份文档有什么内容"：
```
doc1 -> "苹果手机很好用"
doc2 -> "苹果电脑价格贵"
doc3 -> "香蕉苹果都是水果"
```
这份存法回答"doc1 里有什么"很快，但回答"哪些文档提到了苹果"很慢——**必须把 3 份文档全部读一遍，逐个检查**，文档数量一大，这个检查次数跟着线性增长。这正是这次会话里最开始的 `_dense_search()` 在做的事（对每个 chunk 向量算一次相似度），只是换成了向量而不是关键词。

**倒排索引**把这个对应关系反过来存——"每个词，出现在哪些文档里"：
```
"苹果" -> [doc1, doc2, doc3]
"手机" -> [doc1]
"电脑" -> [doc2]
"香蕉" -> [doc3]
"水果" -> [doc3]
```
这样一来，"哪些文档提到了苹果"直接查 `"苹果"` 这一行就有答案，不需要把 3 份文档重新读一遍——**用建索引时多做的一次性工作，换查询时的速度**，这是空间换时间的典型例子。每个词对应的那一串文档编号，专业说法叫 **posting list（倒排列表）**。

### 项目里怎么落地的：`chunks_fts` 这张表，本质就是一个倒排索引，只是 SQLite 帮你管理了

[document_index.py](../src/steward/document_index.py) 里这句：
```sql
CREATE VIRTUAL TABLE IF NOT EXISTS chunks_fts USING fts5(text, tokenize='trigram')
```
`FTS5`（Full-Text Search 的第 5 代实现）是 SQLite 自带的倒排索引引擎——建这张"虚拟表"的时候，SQLite 在背后真正建的不是一张表，是好几张：

```
chunks_fts          <- 你写 SQL 时用的这个名字，只是个外壳
chunks_fts_data      <- 真正的倒排索引数据本体（posting list），压缩过的二进制格式
chunks_fts_idx       <- 索引的 b-tree 结构，加速定位到 chunks_fts_data 里的哪一块
chunks_fts_content   <- 原始文本内容（如果建表时选择自己存储原文，这里会有）
chunks_fts_docsize   <- 每一行(每个 chunk)的 token 数量，bm25 排序要用长度归一化
chunks_fts_config    <- FTS5 自身的配置项(比如版本号)
```
这些表是真实存在的（在你自己的 `steward.db` 里可以直接 `SELECT name FROM sqlite_master WHERE type='table' AND name LIKE 'chunks_fts%'` 查到），只是里面的数据大部分是 SQLite 自己定义的压缩二进制格式，不是能直接用 `SELECT *` 看懂的明文行——这也是为什么"感觉内部实现不清晰"：**不是没有实现，是它被故意封装成了黑盒，你只通过 `MATCH` 这个操作符跟它打交道，不需要（也没法直接）手动摆弄底层的 posting list**。这跟你自己写的 `documents`/`chunks` 这些普通表完全是两回事——那些每一行都是你自己定义的、完全透明的数据。

### trigram 分词具体切的是什么

英文天然按空格分词（"apple phone" 很自然地切成 "apple"、"phone" 两个词去建索引），中文没有空格，"苹果手机"整体是一串连续字符，SQLite 默认的分词器（`unicode61`）按空格切，对中文等于不分词，整句话被当成一个词，几乎没有实用价值。

`trigram` 分词器不管语言，不找词的边界，**固定切"连续 3 个字符"的滑动窗口**：
```
"苹果手机" (4 个字符) 切出来的 trigram:
位置 [0:3] = "苹果手"
位置 [1:4] = "果手机"
```
每个 3 字符片段都单独建一条倒排索引记录。这就是为什么查询至少要 3 个字符才能命中任何东西——查 `"苹果"`（2 个字符）在索引里根本找不到对应的 trigram（索引里存的都是 3 字符的片段），查 `"苹果手"`（3 个字符）能直接对上第一条。这次会话里实测过 `"投资"`(2字) 查不到、`"投资建议"`(4字，内部会被切成 `"投资建"`、`"资建议"` 两个 trigram，用 AND 逻辑同时满足) 能查到，就是这个机制的直接体现。

### bm25 排序，是在倒排索引之上做的事，不是倒排索引本身

倒排索引负责回答"哪些文档命中了"，**bm25 负责回答"命中的这些里，哪个排前面"**——一个词在某份文档里出现得越频繁、但这个词在整个语料库里又不算常见（比如"苹果"到处都是，区分度低；"雷克沙"这种专有名词很少见，区分度高），这份文档的 bm25 分数就越高。这次会话里验证过 bm25 是"数值越小越相关"（反直觉的一点，跟大多数"分数越高越好"的直觉反着来），SQLite 的 `bm25()` 函数就是直接对着 `chunks_fts_docsize`（每行的 token 数量）和倒排索引本身的统计信息算出来的。

## 互联网/后端架构的系统性认知（2026-10-19，计划，还没开始）

**为什么记：** 手头项目都是 AI 方向的 Python 后端，没有"多服务互联网架构"的实践机会；CRUD、表设计能干活，但面试/跳槽需要一套系统性认知，只靠项目实践太慢、也不成体系。**排期：主线仍是把 steward 做健壮、可用，这条等今年手头项目收尾后再开始**，不抢主线。

**起点材料：** 一份互联网架构科普视频的文字稿（单机 → 应用/数据库分离 → 集群+负载均衡 → 缓存 → 读写分离 → 分库分表 → CDN+反向代理 → 搜索引擎+NoSQL → 分布式拆分（RPC/注册中心/消息队列）→ 微服务（链路追踪/限流熔断降级/治理）→ 容器+K8s → 云原生）。骨架有用：每一步都是"瓶颈 → 方案 → 新问题"，正好是系统设计面试的回答结构。**但它只讲了方案的名字，没讲代价**，面试追问的恰恰是代价。

**学习方式：每个节点补成一张表——问题 / 方案 / 新问题（代价）/ 什么时候不该用。** 重点代价清单：
- 缓存：穿透、击穿、雪崩，与数据库的一致性
- 读写分离：主从同步延迟（读到旧数据）
- 分库分表：跨库事务、跨库 join、全局 ID、后期扩容
- 消息队列：丢消息、重复消费、顺序、积压、削峰
- 微服务：分布式事务、最终一致性、排查难度
- 视频末尾三条原则：没有最好的架构只有最适合的；空间换时间、复杂度换性能；围绕高性能/高可用/可伸缩/可扩展/安全

**steward 里已有的同构小规模例子（不是"做过微服务"，别往大了说，但"小规模遇到过同样的权衡"是真话）：**
- 应用与数据库/推理服务分离 → steward 与 llama-server 是两个进程
- 搜索引擎/倒排索引 → FTS5 trigram + bm25，向量检索，RRF 融合
- 空间换时间 → embedding 提前算好存库（bi-encoder）vs 查询时现算的 cross-encoder
- 降级 → llama-server 不在线时跳过打标签，只做 index
- 限流/节流 → refresh 的 30 分钟节流窗口
- 互斥 → refresh 的 PID 锁
- 监控日志 → refresh.log、资源监控
- 容器化的代价 → Docker 在 Mac 上丢 Metal 加速

**三层做法（不用一个大项目）：**
1. **概念地图 + 权衡**（2~3 周兼职量）：上面各节点补表，让 Claude 出题追问。
2. **经典系统设计题口述演练**：短链、秒杀、IM、feed 流，再加一道**网盘/文件同步**（贴公司存储业务，也贴 steward）。
3. **小实验补"痛感"**：docker compose 起 nginx + 两个应用副本 + Redis + Postgres，自己测缓存命中率、杀掉一个副本看高可用。每个一两个小时，不成项目。

**用 AI 服务的视角学，跟 H2 的 AI/Agent 目标互相借力：** 推理服务的负载均衡与批处理（continuous batching，对应 nano-vllm 阅读）、RAG 服务如何扩展、LLM 响应缓存、索引流水线用消息队列。目标岗位的系统设计题大概率是这个味道。

**参考：** 《Designing Data-Intensive Applications》（DDIA，挑章节读）；系统设计面试类书籍。**边界：** 这套学习能把地图建快、把表达练熟，但真实线上经验替代不了，面试里不假装有；小实验的价值就是让自己有真话可讲。
