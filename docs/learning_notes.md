这份文档不是项目状态记录，是这次做 steward 过程中聊到的、值得往"通用工程概念"上抽一层的东西。
每条只记"叫什么、在这个项目里对应哪个具体场景"，不展开讲，方便以后自己查资料时有个起点。

## 幂等性（Idempotency）

**同一个操作重复执行多次，结果都一样，不会因为多跑了几次就出错或者产生副作用。**

项目里的实际例子：
- `upsert_document()` 用 `ON CONFLICT(path) DO UPDATE`——同一个文件路径不管 upsert 多少次，最终状态都一样，不会因为重复调用就产生重复记录。
- `save_tagging_result()` 对标签列表用"先删除这个文档的旧标签、再插入新标签"，而不是简单地往表里 append——不这么做的话，同一个文档被重新打标签两次，标签会累积重复。
- 增量索引那次做的"内容没变就跳过重新处理"，本质也是在利用幂等性：因为重复处理是幂等的（结果一样），所以可以放心跳过没必要的重复。

## 竞态条件（Race Condition）

**两个（或更多）操作同时访问同一份共享状态，最终结果取决于谁先谁后执行到哪一步——顺序不确定，结果就不确定。**

真实踩过的例子（这次 session 里）：不小心同时跑了两个 `index` 进程、都写向同一个 SQLite 文件，其中一个进程执行到一半时另一个进程把数据库文件删了，直接报错——这就是一次真实的竞态条件事故，不是猜测出来的概念。

## 进程间通信（IPC）与"服务"的本质

进程和进程之间没法直接调用对方内存里的函数，必须靠某种通道交换数据：管道（pipe）、共享内存、或者最常见的——socket（HTTP/WebSocket 本质上都是包了一层协议的 socket 通信）。

聊到的场景：桌面应用（Electron/Tauri 的主进程，Node.js 或 Rust）要用现在这套 Python 代码的能力，不是直接调用，是把 Python 打包成一个独立子进程，主进程通过本地 HTTP 服务（或者 stdin/stdout 管道）跟它对话——这就是 IPC 的一个具体应用。

## 什么时候需要起一个"服务"（而不是跑一次退出的脚本）

两个独立的理由，任一成立就该考虑：
1. **需要监听、响应不由人手动触发的事件**——文件变化、插盘、定时任务、UI 请求。从服务自己的代码视角看，这些都是"一直 block 着等一个事件，事件来了就执行对应逻辑"，本质是同一种结构。
2. **摊销重复的启动开销**——比如 embedding 模型每次冷启动都要重新加载，常驻内存能省掉这个反复付出的成本，这条独立于"要不要监听事件"成立。

## SQLite vs 服务端数据库（MySQL/Postgres）的本质区别

不是单纯"有没有并发"，是**数据要不要被多个独立进程（尤其是可能在不同机器上）同时高强度访问**：
- SQLite 是嵌入式库，直接跑在调用它的应用进程里，天生服务"一个应用管自己本机的数据"这个场景，扛得住多个进程"轮流"访问，扛不住"很多进程同时高强度写"。
- MySQL/Postgres 是独立进程，天生要解决"进程外、多方同时访问同一份远程数据"，并发控制能力（连接池、行级锁、MVCC）是这个架构形态带来的必然要求，不是加出来的可选功能。
