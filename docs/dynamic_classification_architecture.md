# 端侧动态语义分类与打标签引擎架构设计方案

本文档记录 Week 3 动态分类模块的架构演进。V1（Cluster-then-Label）是最初的设计，已废弃；V2（逐文件直接分类）是当前正在实施的方案。保留 V1 的记录是为了让后来者（包括未来的自己）看懂"为什么会有这次改动"，不是因为 V1 还在用。

---

## 变更说明：为什么放弃 Cluster-then-Label

### V1 遇到的真实问题

V1 跑通之后，在真实语料（`~/Documents/doc`，482 份文档）上出现了两类反复出现的错误，靠人工翻 `output/tags_report.md` 发现的，不是理论推测：

1. **简历被混进技术教程簇**：`/doc/简历/` 目录下的求职简历，因为写满了 React/Node.js 这类关键词，跟数百篇技术教程在向量空间里几乎无法区分，被 HDBSCAN 分进同一个簇，SLM 看完簇内容后把整个簇命名为"技术代码"，简历也被一起打上这个标签。
2. **聊天记录被临近话题带偏**：`/doc/对话List/` 下的闲聊记录（比如聊音乐、聊旅行）因为"口语化对话结构"相似，被聚进同一个簇，簇里偶然混入了几篇真正聊 ETF 投资的对话，SLM 命名时抓住了投资这个强特征词，把整簇（包括聊音乐、聊旅行的文件）都命名成了"投资理财"。

### 排除掉的修复方向：LLM 预画像（Label-then-Cluster）

第一反应是"让 LLM 先给每个文件写一句画像总结，再拿画像去生成向量、聚类"——这个方案被否决了，原因很直接：这是把 O(K)（只对簇调用 LLM）退化回 O(N)（对每个文件调用 LLM），直接违背了当初设计 Cluster-then-Label 就是为了把 LLM 调用量控制在跟簇数量而不是文件数量挂钩这个初衷。如果要接受 O(N)，那不如干脆让 LLM 直接判断每个文件的分类，没必要再套一层聚类。

### 真正的转折点：一次实测，不是理论推演

否决 Label-then-Cluster 之后，去实测了本地 llama-server（Qwen3.5-2B-Q4_K_M.gguf）跑一次"极短分类 prompt"的真实耗时，而不是继续凭感觉估算。结果：单文件耗时约 0.3~1.2 秒（取决于内容长度和是否并发），全量 1 万文件跑完不到 3.5 小时，用户实际使用场景是"插盘后台跑"，这个耗时完全可以接受。

更关键的是准确性：把之前 V1 判错的 8 个案例（3 份简历、4 份聊天记录、2 份 ETF 投资对话）拿去做"逐文件独立分类"（每个文件单独调用一次 SLM，不依赖聚类簇的集体判断），**全部判对**——简历被正确识别为"求职简历"，音乐/旅行闲聊没有被临近的投资话题拖偏。根源很简单：V1 出错的机制是"一个文件的标签由它所在簇的其他文件决定"，逐文件独立判断从根上避免了这种连带误判。

于是结论是：O(K) 这个约束本身不是必须的，它是为了应对"曾经假设的、其实没验证过的" per-file LLM 调用成本过高这个前提；实测证明这个前提在当前硬件（M4 Pro，本地 Qwen3.5-2B）和当前目标规模（几百到一万）下不成立，架构应该跟着实测数据走，不是跟着最初的假设走。

### V1 被删除的部分，以及为什么不是"可惜"

`clustering.py` 里的 UMAP+HDBSCAN 聚类逻辑、`cluster_llm.py` 里"挑质心文件 → SLM 命名整簇 → 全簇继承"这套机制、`tag_matcher.py` 的矩阵点积批量打标，在 V2 里全部移除，不是标记废弃后继续留在代码里。原因：

- 这套逻辑是为了解决"O(K) 场景下，怎么把一次 SLM 调用的判断结果，合理地分发给一群文件"这个问题存在的；V2 每个文件都单独调用 SLM，不存在"分发"这个需求，这套代码从设计动机上就不再适用，留着只会误导后来者以为它还在生效。
- 如果未来某个具体功能（跨文件关联发现、图片/视频的聚类）真的需要用到 HDBSCAN，到时候按那个功能的实际需求重新写，大概率跟现在这套（针对文本 chunk 向量池化设计的）实现长得不一样，现在留着也未必能直接复用，不如需要时再写。

## V2 设计：逐文件直接分类

### 四阶段管线（原来是五阶段，"置信度复核"这道关卡已撤掉，原因见下面的踩坑记录）

```
已索引文档 (SQLite extractions 表)
    ↓
① 内容量预筛 —— 文本过短/无信息量，直接判 unclassified，跳过 SLM 调用
    ↓
② 逐文件 SLM 分类 —— 并发调用本地 SLM，每个文件独立产出 category + tags + reasoning
    ↓
③ Taxonomy 归一化 —— 对分类名做去重合并（如"前端开发"归并进"技术文档"），所有相关文档的 category 字段同步改写为归一化后的名称。这一步操作对象是分类名字符串，不涉及任何文档向量。
    ↓
④ 置信度计算 —— 文档向量分别跟自己被判定的分类名、标签做点积，作为参考信息存下来，
   不再拿去推翻 SLM 在第②阶段的判断（这个判断本身已经用真实案例验证过是可靠的）
    ↓
写入 SQLite（分类 / 标签 / 置信度落库）
```

### 与 V1 的关键差异

| | V1 (Cluster-then-Label) | V2 (逐文件直接分类) |
|---|---|---|
| LLM 调用量级 | O(K)，K = 簇数 | O(N)，N = 文件数，但单次调用极短、可高并发 |
| 分类粒度 | 簇级判断，广播给簇内全部文件 | 文件级独立判断 |
| 标签来源 | 簇级 tag_pool，矩阵点积分配给簇内文件 | SLM 直接对每个文件产出专属标签，无需再分配 |
| 置信度 | 文档向量与所属簇质心的余弦相似度 | 文档向量与自己被判定的分类名向量的点积（仅供参考，不做判定依据） |
| unclassified 判定 | 未被任何簇收编（含最近质心兜底） | 只看长度预筛 + SLM 解析是否成功，不依赖向量复核 |
| 已验证的失败案例 | 简历混入教程、聊天记录混入投资 | 同一批案例逐一验证通过 |

### 复用与新写

- **原样复用**：`document_vectors.py`（chunk 向量池化）、`embeddings.py`、`extractors.py`、`chunking.py`、`document_index.py`（`save_classification()` 接口不用改）。
- **抽取复用**：`cluster_llm.py` 里的 `_normalize_taxonomy()`（对应第③阶段思路）和 `_extract_snippet()`（html/pdf 正文摘取策略），迁移到新的分类模块里。
- **新写**：新的编排逻辑（替代 `semantic_classifier.run_dynamic_classification_pipeline()`），按上面四阶段串联。
- **删除**：`tagging.py`（`build_classifications`，未被任何地方调用的死代码）、`semantic_classifier.py` 里硬编码关键词规则 `classify_document_text()`（同样是未接入主链路的死代码）、`clustering.py`、`cluster_llm.py` 里聚类相关部分、`tag_matcher.py`（原因见上一节）。

### 已确认的设计决定

- **`semantic_clusters` 表和 `documents.cluster_id` 外键**：不做 schema 迁移，直接删表删字段。`steward.db` 本身不进版本控制，是可以从本地真实文件重新生成的派生数据，写代码时删掉旧库、跑一遍新版 `index` + `classify` 重建（400+ 文件耗时不高），比写一条 `ALTER TABLE DROP COLUMN` 迁移更省事。

### 踩坑记录：置信度复核机制，加了又撤

这一段完整记下来，因为过程本身比结论更值得留档——花了不少功夫加的东西，最后证明方向错了，直接撤掉，不是"以后再优化"，是真的删。

**第一次尝试**：Taxonomy 归一化用一次 LLM 调用处理全部原始分类名（119 个），结果只合并成 57 个，"财务报销"/"发票"/"财务凭证"这种明显同义词都没合并。原因排查出两点：`max_tokens = 分类数×40+200` 在分类数一多就会超过 `n_ctx`（4096），输出被截断；而且 2B 小模型看着一长串抽象字符串自己去发现分组，这个任务本身它就不太擅长。

**第二次尝试**：改成向量相似度分组——算每个分类名的向量，相似度超过阈值的贪心归为一组，只让 LLM 给已经分好的组起名字。第一版阈值拍了 0.80，测出来该合并的对点积只有 0.629~0.869，阈值定太高，几乎不合并。用真实分类名实测校准，"该合并"对和"不该合并"对之间有明显数值空隙，改成 0.60。但很快又发现新问题：像"开发指南"和"出行指南"这种只是共享"指南"两个字、语义完全不同的名字，点积能到 0.7，跟真同义词的数值区间是重叠的——**纯向量相似度这个信号，对短的抽象分类名来说不够干净，没有一个阈值能把这两种情况彻底分开**。

**第三次尝试**：向量分组只当粗筛（允许有假阳性），每组再让 LLM 做一次简单是非题复核："这几个是不是真的一类，有没有字面像但语义不同混进来的"。这版在自己造的 37 个分类名测试集上效果不错（37 归一化到 19，此前离谱的错误合并消失了）。

**真正跑到 477 份真实文档上才发现问题不在归一化，在再往后一步的置信度复核**：122 个原始分类名归一化成 55 个（比第一次好一点，但仍然偏多），357/482（74%）的文档被判成 unclassified。查了这些 unclassified 文档的判定依据，发现**几乎全部**都是同一个原因——"SLM 判定的分类，点积没有排到候选池里第一名"。把这些"差多少"的数字拿出来看分布：从 0.03 到 0.27 连续摊开，中位数只有 0.09，不是"少数明显判错、大多数明显判对"这种两极分化的样子。

这说明问题的性质变了：**不是分类名没归一化干净，是"跟全部候选比大小，必须接近第一名才采信"这套判定逻辑本身有系统性缺陷**——候选分类名有 30~55 个的时候，任何一个语义相近的分类名偶然点积高那么一点点，都会把原本正确的判断打回 unclassified，候选越多，这种偶然发生的概率就越大，不是靠继续磨归一化能根治的统计学问题。而且当初设计这道复核，就是因为不信任 LLM 自己会不会看走眼——但实测下来，SLM 直接判断这件事本身，早就用真实案例（简历、聊天记录这些 V1 会判错的）验证过是可靠的，反倒是这道"复核"自己不可靠，比它想防的问题还严重。

**结论**：撤掉这道复核，点积继续算、继续存，当一个供人参考的数字，不再用来决定 unclassified。unclassified 现在只看两件事：内容是不是太短（第①阶段）、SLM 有没有正常吐出可解析的 JSON（第②阶段）。这不是权宜之计，是基于两轮真实数据（一次证明"信任 LLM 直接判断"是对的，一次证明"不信任、非要拿向量去复核"是错的）之后的正式结论。

### 踩坑记录二：给 Stage② 加"已用分类名"收敛压力，两份语料都验证是错的，已撤

背景：跟 Cowork 独立对比同一批 `~/Documents` 语料后发现，我们逐文件独立判断出来的分类名数量（73/55 个）远多于 Cowork（13 个）。Cowork 靠的是"整个文件夹判断一次、批量复用"，这个具体做法本身依赖它能读懂文件夹结构、还写死了路径规则，不能直接照抄（换目录会失效），但背后的道理——"判断之间应该互相看得见，不要各自为政"——是可以借鉴的一般性原则。

**尝试的做法**：把 Stage② 从"全并发一次性提交"改成"分批推进"，批与批之间累积一份"目前已经用过的分类名"列表，塞进后面每一批的 prompt 里，要求"语义相符时优先复用，不要为相近的内容新建重复分类"。

**结果**：分类名数量确实压下去了（Documents 119→9 个，Downloads 17→13 个），但代价是内容开始被硬塞进不相关的已有分类——Documents 语料里，m-flo 音乐聊天和 ETF 投资聊天都被塞进了"个人指南"；Downloads 语料里更离谱，销售数据分析、英语单词学习进度都被归成了"AI 模型评测报告"，理由文本里模型自己都在牵强附会地找理由。两份完全不同性质的语料（一份整理过、一份零散）上都复现了同一个错误，说明这不是偶然，是这个机制本身的系统性问题。

**结论**：撤掉这个改动，退回 Stage② 完全独立判断。这次教训是一次重要的优先级澄清：**分类名数量多是"不够整洁"，判断内容对不对是"正确性"，两者不是同一个量级的问题，不能拿后者去换前者**。79/55 个分类名但内容全部准确，好于 9/13 个分类名但内容开始串味。Taxonomy 归一化（Stage③）继续保留作为"分类名太碎"的缓解手段（它只处理分类名字符串本身，结构上不会影响文件被分到哪一类），但不再往判断的源头加收敛压力。分类名数量偏多这件事目前维持"知道但接受"的状态，不为了它牺牲准确性。

## 技术附注：n_ctx / slot / KV cache 是怎么回事

这部分是调优本地 llama-server 并发吞吐时确认下来的认知，记录下来供以后回顾，不是 V2 架构本身的一部分。

- **KV cache**：Transformer 推理时，每个 token 在每一层算出的 Key/Value 向量会被缓存下来，生成下一个 token 时不用重新计算历史 token 的 K/V，只需要拿新 token 的 Query 去跟缓存的 K/V 做注意力计算。这是"增量生成"比"每次全量重算"快得多的原因。
- **n_ctx（context size）**：单个 slot 能装下的 token 上限（输入 + 输出累计）。它不是"多轮对话"专属的概念——即使是单轮一次性请求，也需要占用一段 context 空间，只是通常远小于多轮对话累积出来的量。`n_ctx` 这个数字本质就是给 KV cache 缓冲区定的容量上限，llama.cpp 在 slot 创建时会按这个上限直接预分配好内存，不是用多少占多少动态增长的。
- **slot**：服务器预留出来的一条独立"泳道"，每条泳道有自己独立的 KV cache 缓冲区，可以同时处理一个独立请求，彼此互不干扰、不共享。`-np`（`--parallel`）直接决定开几条泳道；`-c`（`--ctx-size`）是**所有泳道的总预算**，服务器按 `-np` 平分给每条泳道（实测验证：`-c 65536 -np 16` 得到每个 slot `n_ctx=4096`，65536÷16=4096 完全对上）。
- **调优方向**：我们的场景是"大量互相独立的单轮短请求"（一个文件一次调用，互不依赖），跟"一个用户的长多轮对话"（少量请求、单个请求 context 越堆越大）需求正好相反——后者要"少泳道、深水池"，我们要"多泳道、浅水池"。默认配置（未指定 `-c`/`-np`）会顺着模型训练支持的最大 context（Qwen3.5-2B 支持 26 万 token）去申请，导致每条泳道预留了远超实际需要的内存，被迫只能开很少的泳道。把 `n_ctx` 降到够用的水平（几千 token），同样的内存预算能开出多得多的并发泳道。
- **并发不是线性提速**：泳道数量决定"能不能同时处理多少个请求"，但每条泳道实际跑起来还是要抢同一块芯片的算力（GPU/CPU 每秒能做的矩阵运算次数是固定的）。实测把泳道从 4 开到 16，总吞吐确实提升了，但只有约 1.6 倍，不是 4 倍——因为算力是硬件决定的天花板，泳道数只决定"有多少人在排队处理"，不决定"处理速度本身能不能超过硬件上限"。
- **Prompt 缓存**：如果新请求开头的一段文字，跟之前处理过的某个请求开头完全一样（比如我们固定不变的分类说明文字），服务器可以直接复用那部分已经算好的 KV cache，只需要真正计算后面变化的部分（比如具体文件内容）。这只加速"读懂输入 prompt"这一段（prefill 阶段），不影响"逐字生成输出"这一段（decode 阶段）。云端 API 里常见的"system prompt caching"功能是同一个机制的产品化包装，不是本质不同的东西。
- **token 数不是跨模型通用的换算单位**：「知道 context window 的 token 上限，就能算出实际占用的内存/显存大小」这句话只在**同一个模型 + 同一套推理引擎内部**成立，换一个模型不能直接套用同一个换算关系。原因：KV cache 每存 1 个 token 实际占用的内存 = 层数 × 注意力头数 × 每头维度 × 2（K 和 V 各一份）× 每个数值的字节数，这几个数字完全由模型自身的架构决定，不同模型（比如我们本地的 Qwen3.5-2B 和云端的 Claude）架构参数天差地别，"存 1 个 token 的成本"可能差出一个数量级。再加上不同模型的分词器（tokenizer）对同一段文字切出来的 token 数量本身也不一样。所以哪怕两边显示的 token 数字面上相同，也完全不能类比或者互相换算——`n_ctx`/`-c` 这套调优结论，只对"llama-server + Qwen3.5-2B"这一套组合成立，换模型要重新实测，不能套公式直接算。
- **`max_tokens` 和 `n_ctx` 不是重复的两道限制**：`n_ctx` 是服务器层面、资源分配意义上的硬上限，一个 slot 起来就定死了，输入 + 输出加起来不能超过它，跟具体某一次请求无关。`max_tokens` 是每次请求自己声明的"这次最多想生成多少字"，只管输出这一段，不同调用可以各自设不同的值。两者要同时满足：`输入 token 数 + max_tokens ≤ n_ctx`。不设 `max_tokens` 理论上也会在撞到 `n_ctx` 时被迫停下，但那是"资源耗尽硬停"，不是"主动控制输出长度"——我们输入才几百 token，`n_ctx` 有 4096，中间有几千 token 的空余，不设 `max_tokens` 的话模型可以啰嗦很久才会被拦下来，既浪费时间又不是我们要的"简短 JSON"，所以要主动设一个跟任务匹配的 `max_tokens`，不能指望靠撞 `n_ctx` 兜底。
- **`temperature`**：控制模型选下一个 token 时的"随机性/敢赌程度"，不是跟 `n_ctx`/`max_tokens` 同一类的资源限制，是纯粹的生成行为参数。数值趋近 0，模型几乎每次都选概率最高的那个 token，输出稳定、可重复；数值调高，低概率的 token 也有机会被选中，输出更多样但也更容易跑偏格式或者内容。分类任务要的是稳定、遵守 JSON 格式、同类文档给出一致的分类名，不是创意多样性，所以两处调用（逐文件分类、taxonomy 归一化）都设了较低的 `0.1`，不是完全的 `0`——纯 0（贪心解码）在个别模型/个别 prompt 下有卡进重复输出循环的已知风险，留一点点随机性能规避。这个具体数值是沿用业界惯例，没有在本项目里专门 A/B 测过，后续如果观察到输出不稳定，这是一个可以回头调的参数。

## 后续规划（未决定优先级，仅记录）

项目结构目前是所有代码平铺在 `src/steward/` 下，没有清晰的分层；执行方式是直接 `python main.py`。这两点被认为不是当前优先级（先把 V2 分类结果做稳定），但已经明确后续方向：项目结构要拆分出更清晰的分层（比如 pipeline / storage / cli），执行方式要改成打包后可通过 `pip install` 分发、用 `steward index/classify/...` 这样的子命令交互，方便同事/领导不用拉代码直接安装使用。

**推理引擎参数（`n_ctx`/`slot` 数）不能跟着产品一起硬编码分发**：现在这套 `-c 65536 -np 16` 的配置，是专门针对开发机（M4 Pro，48GB 统一内存）实测调出来的最优值，一旦打包成 app 分发给同事/领导，对方的硬件（内存大小、有没有 GPU 加速）大概率跟开发机不一样，同一套配置换一台机器可能直接内存溢出，或者慢到没法用。真正要做的是把这次手动"测一遍、调参数"的过程，做成 app 首次启动时自动跑的硬件自检/校准逻辑——探测这台机器的可用内存和加速能力，自动算出适合这台机器的 `n_ctx`/并发数，而不是把开发机上测出来的数字直接写死发给所有用户。这一点目前不需要在 V2 分类管线代码里预先处理，但推理引擎的启动配置这部分要作为一个独立的、后续可替换的配置点来写，不要跟分类逻辑本身耦合，方便以后接上自动校准而不用大改。
