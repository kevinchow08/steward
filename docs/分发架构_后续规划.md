# 分发架构——现状 + 后续要解决的问题

写这份文档的目的：2026-09-11 这次只是解决"给领导一个人分发试用"这个最小
需求，过程中聊出来好几个更大的、值得以后认真做但现在不用做的问题。先记
下来，等真的要往"给更多人用"这个方向推进时，不用重新想一遍。

---

## 一、现状（2026-09-11，给领导一人分发）

### 已经做好、往后也用得上的部分（不是临时糊的）

- **steward 代码本身已经是一个正规的 pip 包**：`pyproject.toml` 定义了
  依赖、入口点（`steward = "steward.cli:main"`）；代码从仓库根的
  `main.py` 挪进了 `src/steward/cli.py`；`config/rules.yaml` 打进包里
  当 package data，用 `importlib.resources` 读取；所有运行时路径统一
  收敛到 `src/steward/paths.py`（数据库/模型/输出都在
  `~/Library/Application Support/Steward/` 下，不依赖源码仓库位置）。
- **bge-m3、bge-reranker-v2-m3 首次运行自动从 ModelScope 下载**
  （`paths.py` 的 `ensure_model_downloaded()`）——判断依据是模型目录下
  有没有 `config.json`，没有就下载，带进度条，下完不再重复下。用
  ModelScope 不用 HuggingFace，是因为国内网络直连 HF 经常连不上，
  ModelScope 上有官方镜像。
- **`tag` 命令支持 `--llm-base-url` / `STEWARD_LLM_BASE_URL` 环境变量**
  ——可以指向任意一台在跑 llama-server 的机器，不再写死 `127.0.0.1`。

### 这次给领导用，还是手动/临时的部分（不是最终形态）

- **embedding + reranker 模型**：今天是 AirDrop 手动拷过去的，不是走
  自动下载（领导人就在现场，AirDrop 比等下载更快，两种方式都能用，
  自动下载这条路已经具备，只是今天没必要用）。
- **2B 大模型（打标签用）**：完全没有分发，**继续跑在 Kevin 自己的笔记本
  上**，领导的 `steward tag` 通过局域网 IP（`llama-server --host
  0.0.0.0` + `STEWARD_LLM_BASE_URL=http://<Kevin的局域网IP>:8080/v1`）
  连过来推理。**这个方案的前提是"同一个 WiFi + Kevin 的笔记本得开着"**，
  只适合"一个人、当面、临时"这种场景，不是能长期依赖的架构。

**一句话总结现状**：steward 代码本身的分发已经比较成熟；embedding/
reranker 模型的分发也基本解决（自动下载）；**唯一还完全没解决、纯靠
"人肉+局域网"撑着的，是 2B 大模型的分发/部署问题**。

---

## 二、以后真要往"给更多人用"推进时，要解决的问题

### 问题 1（最大的一个）：2B 模型怎么摆脱"必须连 Kevin 的笔记本"

现在的架构：`llama-server`（llama.cpp 编译出来的独立二进制）常驻 Kevin
的笔记本，其他人的 `steward tag` 走网络连过去。这个模式的天花板很低：
离不开 Kevin 的电脑、离不开同一个局域网、Kevin 电脑一睡眠/断网/关机就
全部瘫痪，也谈不上支撑多人并发。

聊过的候选方案，**都还没验证，下次要做的时候需要实测比较**：

- **方案 A：`llama-cpp-python`（llama.cpp 的官方 Python 绑定）**——
  pip 直接装（`pip install llama-cpp-python`），可以像
  `LocalEmbedder`/`LocalReranker` 现在的用法一样，**在 steward 自己的
  Python 进程里直接加载 GGUF 模型做推理，不用另外起一个 `llama-server`
  子进程、不用局域网通信**。如果这条路走通，`tag` 命令能变得和
  `search`/`index` 一样"纯本地、单进程、装完就能用"。
  **待验证**：
  - Apple Silicon 上 Metal GPU 加速是否好装（查到的资料显示可能需要
    `CMAKE_ARGS="-DGGML_METAL=on"` 源码编译，不一定有现成 wheel，需要
    Xcode 命令行工具）
  - 推理速度是否能达到现在 `llama-server` 的水平（参考基线：~115
    token/s，见 `SUMMARY.md` 那次视觉模型测试的数据）
  - 2B 模型换成"进程内加载"之后，跟 embedder/reranker 是不是要在同一个
    Python 进程里共存，会不会导致内存占用比现在"三个独立进程"更高
    （PyTorch/Metal 对显存的释放不一定干脆）
  - 2B 的 GGUF 权重本身能不能也走 ModelScope/HF 自动下载（还没查证过）

- **方案 B：Ollama 接管 2B 模型的下载 + 服务管理**——Ollama 本身就是
  "一个简单安装、自动下载模型、自动管理本地服务、暴露 OpenAI 兼容接口"
  这一整套问题的成熟方案（`brew install ollama`，`ollama pull` 拉模型）。
  `tagging.py` 现在调 LLM 已经是走 `OpenAI` 客户端，理论上把 base_url
  指向 Ollama 的本地服务，代码几乎不用改。
  **待验证**：Ollama 对 Qwen3.5-2B 这个具体模型的支持情况、以后如果做
  图片方向，Ollama 对视觉模型（mmproj）的支持成熟度够不够。

- **方案 C：真正意义上的常驻共享服务器**（不是 Kevin 的笔记本，是一台
  一直开着的机器）——集中式部署，但会重新引入"用户的文件内容要发出去做
  推理"这个隐私上的让步，跟"端侧"的定位有冲突，是否要走这条路需要更
  谨慎地权衡，不是纯技术决定。

**下次要做的时候，建议的验证顺序**：先在自己机器上分别试一遍方案 A 和
方案 B（重点看 Metal 加速好不好装、性能对不对得上、以后图片模型能不能
复用同一套机制），两者对比之后再决定往哪个方向重构 `tagging.py` 的
LLM 调用方式。

### 问题 2：模型数量/体积会持续增长，需要守住的设计纪律

现在已经有 3 个模型（bge-m3、bge-reranker-v2-m3、Qwen3.5-2B），以后
图片/视频方向一旦做，还会再加。这不是这个项目设计得不好，是端侧 AI
本身的代价（每个真实能力背后都是一个专门训练的模型，没法合并），但有
几条原则值得以后一直守住，不是"以后再说"：

- **按需下载，不用的能力不占地方**——现在 `index`/`search`/`tag`/
  `duplicates` 各自只拉自己需要的模型，这个原则要延续到以后新增的
  每一个能力上。
- **同一类能力，优先评估更小的模型变体**——比如 bge-m3 有个体积小
  20 倍的近亲 `bge-small-zh`，要不要换，取决于精度够不够用，这是个
  以后可以拿真实语料测的事。
- **不是所有能力都需要一个新模型**——摄影 QC（模糊/曝光检测）这类，
  经典图像处理算法就能做，零模型成本，加新能力时先问一句"真的需要
  训练过的模型吗"。

### 问题 3：wheel/代码怎么交付给更多人（人数上来之后再考虑）

现在（1~几个人）直接传文件 / 放企业网盘就够，见
`docs/分发安装说明.md`。人数明显变多之后，可以考虑 `pip install
git+内部git地址` 或者搭一个私有 PyPI 源（`pypiserver`/`devpi`/公司的
Nexus），不是现在的优先级，先记着这条路存在。

### 目标状态：一个陌生人也能快速体验，不用任何局域网通信

这是所有问题解决之后应该达到的效果：`pip install steward` → 首次运行
各个命令按需从 ModelScope（或以后换成的下载源）自动拉自己要的模型
（包括 2B 模型，一旦问题 1 解决）→ **全程零局域网依赖、零
`STEWARD_LLM_BASE_URL`、零"必须有台机器开着 llama-server"**——装完
就是完整、独立、能自己跑起来的体验。今天给领导的方案是达到这个目标
之前的一个过渡桥梁，不是终点。
