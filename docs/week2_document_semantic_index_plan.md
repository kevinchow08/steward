# Week 2：document 内容理解与本地语义索引方案（待 Review）

## 1. 这周到底要解决什么

领导的原始方向是“分类、打标签，并最终产品化”。Week 1 已经完成了第一层：它能判断文件的**技术类型**，例如 document、image、archive。这很重要，因为它决定了文件可以走哪条后续处理路线；但它不能回答“这份文档是关于什么的”。

Week 2 不急着发明一套封闭的业务分类，也不把聚类编号当产品功能。目标是先建立 document 的内容理解地基，并验证它是否对用户有价值：

> 用户用自然语言描述想找的内容时，系统能否只在本机上找回内容相关的文档，并说明匹配到了哪里？

若这个闭环成立，后续的分类、标签、摘要、RAG 检索和整理建议都会复用同一套文本与向量基础设施；若它不成立，也能尽早知道端侧方案的真实边界，而不是在自动整理阶段才暴露问题。

## 2. 概念边界

以 `上海差旅报销单.pdf` 为例：

| 名称 | 回答的问题 | 示例 | Week 2 是否实现 |
| --- | --- | --- | --- |
| 技术类型 | 文件格式/处理路线是什么？ | `document`、PDF | 已由 Week 1 提供 |
| 语义分类 | 它主要属于什么业务内容？ | 财务材料 | 否，后续定义 |
| 标签 | 它有哪些可并存的检索特征？ | 报销、差旅、上海、2026 | 否，后续才建议/确认 |
| 语义索引 | 怎样通过内容把它找回来？ | 文本片段 + 向量 + 元数据 | 是 |
| 决策/行动 | 下一步应如何处理它？ | 建议移到某目录，等待确认 | 否，严格排除 |

“分类”通常是一份文件的主要归属；“标签”可以有多个，且可以随用户习惯演进。两者都不应由 Week 2 先拍脑袋固定下来。

## 3. 最小产品切片

### 用户路径

```text
用户选择一个目录
    ↓
扫描并筛出 document 文件（复用 Week 1）
    ↓
从支持格式中提取本地文本
    ↓
将文本分段、生成本地 embedding、写入本地 SQLite 索引
    ↓
用户输入自然语言查询
    ↓
展示相关文件的路径、文件名、匹配片段、相似度
```

示例：用户查询“去年上海出差的报销材料”。系统返回若干匹配文档及其命中的文字片段。用户可以据此判断结果是否真的相关；系统不移动、不改名、不写标签到任何原始文件。

### 本周可交付物

1. 一个可重复运行的 document 索引命令。
2. 一个本地自然语言检索命令。
3. 一个 SQLite 索引文件与可读的运行报告：支持/跳过/失败文件数、失败原因、耗时和资源数据。
4. 一组人工编写的真实查询及观察结果，用于汇报端侧语义检索是否有用。

## 4. 明确范围

### 纳入范围

- 输入目录及其子目录中的 `basic_type == "document"` 文件。
- 第一批文本格式：PDF、DOCX、TXT、Markdown、HTML；结构化数据格式加入 CSV、TSV、XLSX，XLS 以真实样本确认。
- 本机文本提取、本机 embedding、本机 SQLite 数据库、本机相似度计算。
- 文档分段、自然语言查询、按相关性返回文件和匹配片段。
- 文件处理状态和资源指标的可见记录。

### 暂不纳入范围

- 扫描件 OCR、图片、PPT、旧式 DOC、RTF/ODT 的内容提取。它们仍保留在 Week 1 的统计里，但索引报告要标为 `unsupported` 或 `no_text`，不能伪装为成功。CSV/TSV/XLSX 纳入本周内容索引，XLS 以真实样本确认。
- 自动业务分类、自动打标签、自动摘要、聊天式问答。
- HDBSCAN 作为正式交付、向量数据库、Web UI、Finder 标签同步。
- 任何文件移动、删除、重命名或写回标签的行为。

## 5. 技术方案

### 5.1 输入与处理流程

索引操作每次从目标目录重新执行 Week 1 的扫描与类型识别，避免依赖可能过期的 `output/results.json`。只把 `basic_type == "document"` 的路径交给内容处理层。

| 阶段 | 输入 | 输出 | 关键原则 |
| --- | --- | --- | --- |
| 扫描/路由 | 目录 | document 文件路径 | 复用 Week 1，不重复维护类型规则 |
| 文本提取 | 单个 document | 原文文本或明确失败状态 | 一文件失败不阻塞整批 |
| 清洗/分段 | 提取文本 | 带序号的文本片段 | 保留原始顺序，避免静默改写语义 |
| 向量化 | 文本片段 | embedding 向量 | 仅使用本地模型推理 |
| 持久化 | 元数据、片段、向量 | SQLite 索引 | 原始文件只读 |
| 查询 | 用户自然语言 | 排序后的文件与片段 | 结果可解释、可人工检查 |

### 5.2 文本提取规则

| 格式 | 首选库 | 预期处理 |
| --- | --- | --- |
| PDF | `pypdf` | 提取文字层；空文本的扫描件记录为 `no_text` |
| DOCX | `python-docx` | 读取段落文字；表格支持不属于第一版承诺 |
| TXT / MD | Python 标准库 | 先尝试 UTF-8 系编码；解码失败记录原因 |
| HTML | `beautifulsoup4` | 去除脚本/样式后提取可见文本 |
| CSV / TSV | Python 标准库 | 保留表头与行列关系，按行块转换为可检索文本 |
| XLSX | `openpyxl` | 按工作表读取，保留工作表名、表头和行值 |
| XLS | 待读取库 | 与 XLSX 采用同一结构化文本格式，先用真实样本确认兼容性 |

文本保留在本地数据库中，目的是在检索结果中展示匹配片段，也为后续摘要/标签提供基础。文档内容不发送到外部服务；模型文件默认下载到项目根目录的 `models/bge-m3/`，首次下载是显式的本地准备步骤。

### 5.3 分段与 embedding

一份长文档不能直接塞给 embedding 模型：模型有输入长度上限，且整篇混合主题会稀释检索效果。因此以段落为边界累积成适中片段；第一版建议目标约 800 个字符、相邻片段约 100 个字符重叠。实际实现时以中文字符数近似控制，先保持规则简单、可解释。

每个片段生成一个向量。查询也生成一个向量，通过余弦相似度比较查询与所有片段：

1. 取相似度最高的片段；
2. 按文件去重，每个文件保留其最佳片段；
3. 返回前 N 个文件、相似度和对应片段。

对于本项目当前规模（数百份文档），直接在内存中比较全部向量足够，且比引入向量数据库更容易理解和调试。数据量和性能证明需要时再评估专用向量索引。

### 5.4 模型选择：先定标准，再做一次小样本确认

模型是 Week 2 唯一需要实际验证的关键选择，不能仅凭模型名拍板。当前默认路线是 `sentence-transformers + BAAI/bge-m3`：它支持中文及多语言文本，直接提供本地 embedding 接口；最终仍以少量真实样本验证结果为准。后续如果要统一到 llama.cpp 生态，只需使用相同的数据契约重建向量，不改变文件、文本和片段表。

候选必须同时满足：

- 支持中文为主、兼顾中英文混合文件；
- 可在 Apple Silicon 本地运行；
- 提供明确的向量维度和查询/文档编码方式；
- 模型与推理依赖的许可证适合原型及未来产品评估；
- 在小样本上能把明显相关文档排在不相关文档之前；
- 模型加载时间、向量化速度和内存可接受。

实现前用少量真实但非敏感的文档和 5 条查询做一次模型选择记录。Week 2 的代码需把 `model_id`、向量维度和索引版本写入数据库，保证之后能追溯“这个结果由哪个模型产生”。如果更换模型，必须重建对应向量，不能混用。

### 5.5 本地数据模型

SQLite 足够作为第一版产品化基础，且 Python 自带 `sqlite3`，不需要服务器。建议包含以下逻辑表：

| 表 | 关键字段 | 用途 |
| --- | --- | --- |
| `documents` | `id`、`path`、`size_bytes`、`mtime_ns`、`basic_type`、`extract_status`、`extract_error`、`text_char_count` | 文件身份与提取状态 |
| `chunks` | `id`、`document_id`、`chunk_index`、`text` | 可显示的文本片段 |
| `embeddings` | `chunk_id`、`model_id`、`dimension`、`vector_blob` | 片段向量及其版本信息 |
| `index_runs` | `id`、开始/结束时间、模型信息、统计 JSON | 每次运行的可追溯报告 |

字段关系说明：

- `documents.id`、`index_runs.id`、`extractions.id`、`chunks.id`、`embedding_models.id` 是各自表的主键（Primary Key），用于唯一标识一条记录。
- `documents.last_seen_run_id` 是外键（Foreign Key），引用 `index_runs.id`，表示这个文件最近一次在哪个索引任务中被看见。
- `extractions.document_id` 是外键，引用 `documents.id`；一个文件当前保留一份提取结果。
- `chunks.extraction_id` 是外键，引用 `extractions.id`；一份提取结果可以有多个 chunk。
- `embeddings.chunk_id` 是外键，引用 `chunks.id`；`embeddings.model_id` 是外键，引用 `embedding_models.id`。
- `ON DELETE CASCADE` 只用于父子数据的清理：删除一份 extraction 时，属于它的 chunks 会自动删除；删除 chunk 时，属于它的 embeddings 会自动删除，避免留下无法关联的孤儿记录。

当前表的约束与字段含义：

| 表 | 字段 | 约束/含义 |
| --- | --- | --- |
| `index_runs` | `id` | 主键，自增 |
| `index_runs` | `started_at` / `ended_at` | 本次索引任务的开始/结束时间 |
| `index_runs` | `model_name` / `model_dimension` | 本次任务使用的 embedding 模型及向量维度 |
| `index_runs` | `stats_json` | 本次任务的统计信息，保存为 JSON 文本 |
| `documents` | `id` | 主键，自增 |
| `documents` | `path` | 文件路径，唯一；当前用它识别文件 |
| `documents` | `size_bytes` / `mtime_ns` | 文件大小与修改时间，用于后续判断是否变化 |
| `documents` | `basic_type` | Week 1 的基础类型 |
| `documents` | `is_present` | 最近一次扫描是否还看到这个文件，1/0 |
| `documents` | `last_seen_run_id` | 外键，指向最近一次见到它的索引任务 |
| `extractions` | `id` | 主键，自增 |
| `extractions` | `document_id` | 外键，且唯一；指向所属文件 |
| `extractions` | `status` / `error` | 提取成功、无文字、失败等状态与原因 |
| `extractions` | `full_text` / `char_count` | 完整提取文本与字符数 |
| `chunks` | `id` | 主键，自增 |
| `chunks` | `extraction_id` | 外键，指向所属提取结果 |
| `chunks` | `chunk_index` | 在该文件中的顺序编号 |
| `chunks` | `text` / `start_offset` / `end_offset` | 片段内容及其在原文中的位置 |
| `embedding_models` | `id` | 主键，自增 |
| `embedding_models` | `model_name` / `dimension` / `normalized` | 模型身份、向量维度和归一化状态；组合唯一 |
| `embeddings` | `chunk_id` / `model_id` | 复合主键，同时也是两个外键 |
| `embeddings` | `dimension` / `vector` | 向量维度与 float32 二进制内容 |

向量以 SQLite BLOB 保存；查询时加载当前模型对应的向量到内存并计算余弦相似度。第一版每次可全量重建，以获得最简单、可靠的结果。后续再依据 `path + size + mtime_ns` 复用未变化文件的文本和向量，避免过早实现增量更新复杂度。

## 6. 验收与汇报方式

### 人工验证集

建立一份不提交敏感正文的查询清单，包含约 10 条来自真实使用场景的描述，例如“去年的差旅报销”“某项目的周报”“租房相关文件”。每条记录人工预期能找到的 1～数个文件。

不在不了解语料前假设一个虚假的“准确率 90%”门槛；第一轮记录以下事实：

- 预期文件是否出现在 Top 5；
- 结果中是否有明显无关文件；
- 查询措辞变化是否明显影响结果；
- 哪些格式提取失败或没有文字层；
- 向量化、查询与资源占用数据。

### 对领导可展示的内容

1. Week 1：文件技术类型路由与资源基线已经完成。
2. Week 2：对真实本地文档，输入自然语言可返回内容相关的文件和命中片段；全程仅在端侧处理。
3. 边界也透明展示：扫描件、未支持格式和低相关结果不会被伪装成“理解成功”。
4. 下一步依据检索结果与真实使用反馈，定义哪些语义分类/标签值得自动建议；再逐渐进入“建议整理、用户确认”的 Agent 交互。

## 7. 与后续产品的关系

```text
Week 1：技术类型路由
    ↓
Week 2：document 文本 + embedding + 本地语义索引
    ↓
候选标签/语义分类（带置信度与 unclassified 回退）
    ↓
只读产品：检索、摘要、标签展示
    ↓
可逆建议：归档、重命名、去重，等待用户确认
    ↓
Agent 决策/行动：只在可解释、可确认、可恢复的策略下执行
```

聚类可以在 Week 2 索引数据之上再做：它帮助发现可能的主题和标签，但不是检索、标签或行动的唯一前提。新文件始终允许是 `unclassified` / `other`；只有高频且用户觉得有价值的新主题，才会被加入分类或标签体系。

## 8. Review 后才进入代码的决定项

以下项目必须在实现前共同确认：

1. 上述 Week 2 目标是否替换原先“聚类为主要交付”的目标；
2. 是否认同 PDF、DOCX、TXT、MD、HTML、CSV、TSV、XLSX 为第一批格式，XLS 用真实样本确认；
3. 是否认同 SQLite + 全量向量比较作为第一版，而不引入向量数据库；
4. 是否认同“文档分段后检索”而非每份文件只生成一个向量；
5. 默认使用 `sentence-transformers + BAAI/bge-m3`，并在小样本上记录结果；
6. 最小 CLI 的具体形式，以及索引是否放在 `output/steward.db`；
7. 用于验收的真实查询场景和样本目录范围。

在这些点得到确认前，不开始实现 Week 2 功能代码。
