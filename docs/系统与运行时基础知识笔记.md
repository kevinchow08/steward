# 系统与运行时基础知识笔记

写这份文档的背景：给 `steward refresh` 功能选调度方案（launchd）的过程中，牵出了一长串更底层的问题——launchd 是什么、服务和进程有什么区别、可执行文件到底是什么、pip install 具体做了什么、venv 怎么隔离环境。这些认知不直接影响 steward 的业务逻辑，但反复被问到、反复需要用到，属于"该焊牢但一直悬着"的地基知识，值得单独存一份，不想只留在聊天记录里，之后可以直接回来翻、继续追问。

## 一、launchd——macOS 的服务管理器

`launchd` 不是"定时任务"这么简单，是 macOS 整个系统的服务管理器（PID 1，开机第一个启动的进程），角色上对应 Linux 的 `systemd`。你写一份 XML 配置文件（plist），放到指定目录，launchd 负责"什么时候启动这个程序、要不要保活、崩了要不要拉起来"。

**两类关键目录**（运行身份不同）：
- `~/Library/LaunchAgents/`——用户级，要等这个用户**登录**之后才会被加载生效，不是"开机就生效"（这是个容易搞混的点：开机但停在登录界面、还没人登录的那段时间，这类任务还没启动）。
- `/Library/LaunchDaemons/`——系统级，开机就跑，不需要任何人登录，跑在 root 权限下。

**触发方式，不止"定时"一种**：

| 配置项 | 含义 |
|---|---|
| `StartCalendarInterval` | 像 cron，指定具体时间点（"每天 3 点"） |
| `StartInterval` | 固定间隔重复跑（"每隔 N 秒"） |
| `KeepAlive` | 进程退出就立刻重新拉起来，让它一直活着——**这是"常驻服务"的开关** |
| `WatchPaths` | 监听指定路径，路径下有变化就触发跑一次——底层用系统原生的 FSEvents 机制，不需要自己写一个常驮进程去监听 |
| `RunAtLoad` | 登录/加载这份配置时就跑一次 |

**steward 用的是 `WatchPaths`（不是定时），配合应用层的节流逻辑**（见 `refresh.py` 的 `THROTTLE_SECONDS`），因为"文件变了尽快同步"比"固定时间点才同步"更贴合需求，同时不需要为此常驻一个进程。

**真实的 plist 长什么样**（对应 `refresh.py` 的 `_build_plist_content()`）：
```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.steward.refresh</string>
    <key>ProgramArguments</key>
    <array>
        <string>/Users/kevinchow/.../venv/bin/steward</string>
        <string>refresh</string>
    </array>
    <key>WatchPaths</key>
    <array>
        <string>/Users/kevinchow/Documents</string>
    </array>
    <key>StandardOutPath</key>
    <string>.../refresh_stdout.log</string>
    <key>StandardErrorPath</key>
    <string>.../refresh_stderr.log</string>
</dict>
</plist>
```
`ProgramArguments` 本质就是命令行的 argv，`launchd` 拿这个数组去执行，效果跟自己在终端敲 `steward refresh` 完全一样。

**常用 `launchctl` 命令**：
```bash
launchctl load ~/Library/LaunchAgents/com.steward.refresh.plist    # 注册/加载
launchctl unload ~/Library/LaunchAgents/com.steward.refresh.plist  # 卸载
launchctl list | grep steward                                      # 确认已注册
launchctl start com.steward.refresh                                 # 立刻手动触发一次，不用等真实触发条件
```
**关键细节**：改了 plist 内容之后，光改文件不会自动生效，必须 `unload` 再 `load` 一遍；但只要文件本身放在 `~/Library/LaunchAgents/` 下，**以后每次登录 launchd 都会自动重新扫描加载**，不需要每次手动重新 `load`。

## 二、内核 / 进程 / 服务 / PID / 活动监视器——五个概念分清楚

- **内核（kernel）**：操作系统里权限最高、直接管理硬件（CPU、内存、磁盘、网络）的那部分程序。所有其它程序要做涉及硬件的事，都得通过内核提供的接口（系统调用）。macOS 的内核叫 XNU，Linux 的内核就叫 Linux。开机时内核第一个启动，它启动的第一个用户态程序就是 `launchd`（所以 `launchd` 的 PID 永远是 1）。

- **进程（process）**：一次程序运行的具体实例，有自己的内存空间、自己的 PID，从启动到退出是一个"有始有终"的存在。崩了重启，严格说是一个全新的进程，拿到全新的 PID。

- **服务（service）**：更持久、更抽象的概念——是"这个程序应该按什么规则运行"这份**配置/约定本身**（plist 里定义的"该不该常驻、该不该重启、监听哪些路径"），不是某一次具体运行。服务的身份由 launchd 持续维护，背后可能换过好几个不同的进程实例（每次崩溃重启都是新 PID），但"这还是同一个服务"。**`com.steward.refresh` 这个服务本身持续存在，但它每次被触发都是全新的、独立的进程，跑完进程退出，服务本身还在，等下次触发。**

- **PID（Process ID）**：操作系统给每个正在跑的进程分配的唯一编号，同一时刻不重复，进程退出后编号可能被复用。`os.getpid()` 拿到的是当前这次运行自己的编号。

- **活动监视器**：一个**观察+手动操作的工具**，把内核维护的"进程表"用图形界面展示出来，你能看、能手动杀，但它自己不参与"要不要启动/保活"这个决策——这个决策是 launchd 在做。类比：活动监视器之于进程表，就像 TablePlus 之于数据库表——都是"图形化查看/手动操作某个底层数据结构的窗口"，本身不是那个真正驱动业务逻辑的引擎。

## 三、"可执行文件"（bin）到底是什么——三种不同的东西，别混为一谈

操作系统"执行"一个文件之前，要先看文件**开头几个字节**判断"这是什么、该怎么处理"——这跟 steward 自己 Week 1 写的"用 magic bytes 判断文件类型"是同一个机制，只是这次做判断的是操作系统内核。

**情况一：真机器码（严格意义上的"二进制文件"）**
C/C++/Rust/Swift 经过**编译器**（`gcc`/`clang`/`rustc`）翻译成 CPU 能直接执行的指令，针对特定芯片架构（ARM64/x86_64）。文件开头是特定的格式魔数（macOS 叫 Mach-O，Linux 叫 ELF）。内核识别出来之后，直接把机器码加载进内存、让 CPU 跳过去执行，中间不需要任何翻译。**项目里的例子**：`llama-server`（C++ 编译）、以后如果做 Tauri，那个 App 本体（Rust 编译）。

**情况二：解释型脚本，"伪装"成可执行文件**
文件开头两个字节是 `#!`（shebang），后面跟着另一个程序的路径（比如 `#!/venv/bin/python3.13`）。内核看到 `#!` 开头，把执行请求**转发**给这一行指定的程序，让它去解释执行脚本剩下的内容。**`pip install` 生成的 `~/venv/bin/steward` 就是这一类**——它不是真正的二进制文件，是一个很小的文本文件，第一行是精确到小版本号的解释器路径，后面几行代码等价于：
```python
from steward.cli import main
sys.exit(main())
```
`llama-server` 那种真机器码，跟我们这个 `steward` 脚本，**根本不是同一类东西**，只是日常说话都被笼统叫"bin"，这是模糊的根源。

**情况三：打包封装成自包含可执行文件**（比如 `PyInstaller`）
把 Python 解释器本身 + 全部依赖库 + 你的代码，一起打包进一个文件，行为上从外部看接近情况一（不需要目标机器预装 Python），但内部原理依然是解释执行，不是真编译。**Electron/Tauri 的"外部 bin"，如果要不依赖用户机器预装 Python，通常需要走这条路，不能直接分发情况二那种脚本。**

**三种对比**：

| 类型 | 例子 | 要不要编译 | 目标机器要不要预装对应运行时 |
|---|---|---|---|
| 真机器码 | `llama-server`、Tauri App 本体 | 要 | 不需要 |
| 解释型脚本 | 现在的 `~/venv/bin/steward` | 不要 | 需要预装解释器 |
| 打包封装 | PyInstaller 打包后的 steward | 不算真编译，但打包成一个文件 | 不需要 |

**Electron vs Tauri 的主进程，机制不一样**：
- **Electron**：你写的 JS 全程不编译，是 Electron 官方预编译好的大二进制（内置 Chromium + Node.js）在运行时解释执行你的 JS——App 本体其实是"Electron 这个已编译程序在跑你的脚本"。
- **Tauri**：你写的 Rust **真的会被编译**（`cargo build`），生成的二进制就是 App 本体。

**一个完整的桌面 App，有三个不同角色，别并成一句话**：
1. **主进程**（自己的控制逻辑）
2. **渲染进程**（UI/webview，框架自带组件，**不是**一个被单独执行的外部 bin）——主进程和渲染进程之间靠框架自带的 **IPC 机制**（Electron 的 `ipcMain`/`ipcRenderer`，Tauri 的 `invoke`）通信。
3. **后端 sidecar**（比如我们的 steward Python 程序）——这才是真正"主进程去执行一个外部 bin"的场景，主进程把它当子进程拉起来，通信走的是 **HTTP 请求**，不是 IPC。

两条通信线路，服务两个不同的关系，不该被压成一句"主进程执行 bin 跟渲染进程通信"。

## 四、`pip install xxx.whl` 具体做了什么

`.whl` 本质是个 zip 压缩包（后缀名不同，格式基本一致），**它自己不是可执行的东西，是给 `pip` 读的安装包**。

1. **确定往哪个 venv 装**——取决于有没有先激活某个 venv。
2. **解压 wheel**——拿到源码文件 + 元数据（从 `pyproject.toml` 编译出来的：包名、版本、依赖清单、`[project.scripts]` 定义的入口点）。
3. **递归安装依赖**——读依赖清单，去 PyPI 下载每一个依赖的 wheel，同样装进这个 venv；这些依赖自己可能还依赖别的包，一路递归装到齐——**第一次安装耗时几分钟，大头都在这一步，不是我们自己的代码**。
4. **拷贝源码进 `site-packages/steward/`**。
5. **按 `[project.scripts]` 生成入口脚本**——`steward = "steward.cli:main"` 这一行，生成情况二讲的那个 shebang 脚本，写进 `bin/steward`。
6. **写一份"这次装了什么"的记录**（`*.dist-info`），方便以后 `pip uninstall`/`pip list` 能查、能干净卸载。

## 五、venv（虚拟环境）到底是什么

**要解决的问题**：如果这台机器只有一份全局 Python，两个项目需要不同版本的同一个包（比如 `numpy` 新旧版本），没法同时满足；乱改全局环境还可能连累系统自己依赖 Python 跑的东西。

**venv 是给每个项目单独造一份隔离的 Python 世界**，目录结构：
```
.venv/
├── bin/
│   ├── python3      → 通常是个符号链接（这台机器上验证过，甚至可能就是同一份物理文件）
│   ├── steward        （项目专属的入口脚本，pip install 时生成）
│   └── activate       （下面第六节讲）
├── lib/python3.13/site-packages/
│   ├── steward/       ← 我们自己的源码
│   ├── numpy/         ← 依赖
│   └── ...
└── pyvenv.cfg          （记录这个 venv 是基于哪个解释器创建的，见第七节）
```

## 六、`source .venv/bin/activate` 到底做了什么

**先说 `source`（等价于 `.`）本身的含义**：正常执行一个脚本（`./script.sh`），操作系统会开一个**新的子进程**去跑它，子进程改自己的环境变量，跟当前终端（父进程）没关系，子进程一结束这些改动全部消失。`source` **不开新进程，是直接在当前这个终端会话里，把脚本里的命令当成你自己敲的去执行**——所以脚本里的 `export PATH=...` 改的就是你当前终端自己的 `PATH`，脚本"跑完"之后改动会一直留着。

**`activate` 脚本具体做的事**：
1. 把当前 `PATH` 先备份一份。
2. **把 `.venv/bin` 塞到 `PATH` 最前面**——`PATH` 是一份"按顺序找命令"的目录清单，shell 找命令是从前往后找，找到第一个匹配就用。塞到最前面，意味着之后敲 `python`/`pip`/`steward`，一定先命中这个 venv 自己的版本。
3. 改一下终端提示符（`PS1`），显示 `(venv)` 前缀。
4. 定义 `deactivate` 函数，负责把第 1 步备份的 `PATH` 恢复回去。

**真实验证过的效果**（这台机器上跑出来的）：
```
激活前 PATH 第一行: /opt/homebrew/opt/postgresql@15/bin
激活前 which python3: /opt/homebrew/bin/python3

激活后 PATH 第一行: /Users/kevinchow/CodeKevin/steward/.venv/bin
激活后 which python3: /Users/kevinchow/CodeKevin/steward/.venv/bin/python3

deactivate 后：一切恢复原样
```
**没有配置文件被改、没有东西被安装、没有系统级的任何变化**——纯粹是"这一个终端窗口，接下来查找命令的顺序，临时被调整了一下"，关掉窗口自动作废。

**为什么 `launchd` 不需要激活**：`setup_schedule()` 拿的是 `sys.argv[0]` 解析出来的**完整绝对路径**，不依赖 `PATH` 这份查找清单去"找"命令，直接拿绝对路径执行。"激活"只是给人在终端手动敲命令用的便利（少打几个字），程序之间互相调用、launchd 触发任务，从来不需要它。

## 七、解释器版本隔离 vs 包隔离——两个独立的维度，别搞混

这台机器上验证过一个反直觉的事实：**steward 这个项目的 `.venv/bin/python3` 和系统全局的 `python3`，一路追踪到底，是完全同一个物理文件**（`/opt/homebrew/Cellar/python@3.13/.../python3.13`）。

**这不代表 venv 的隔离是假的**，是因为要区分两个独立维度：

1. **包隔离**（不同项目用不同版本的 numpy 这种）——**不需要不同的解释器文件**。靠的是 `pyvenv.cfg` 这份配置：Python 解释器启动时，会检查自己是从哪条路径被调用的，如果旁边（或上一级目录）躺着一份 `pyvenv.cfg`，就知道"这次是通过某个 venv 被调用的"，于是改用这个 venv 专属的 `site-packages` 去找包，而不是全局那份。**区分的依据是"从哪条路径调用它"，不是"用了哪个解释器文件"**——同一个解释器文件，走不同路径调用，行为不一样。

2. **解释器版本本身隔离**（Python 3.11 vs 3.13）——**必须靠真正不同的解释器文件**，这是机器码层面的差异，任何配置文件都改不了。venv 创建那一刻（`python3.13 -m venv .venv`），就已经决定死了这个 venv 绑定哪个版本，记在 `pyvenv.cfg` 的 `home = ...` 那一行。

**这台机器上验证过：Homebrew 只装了 `python@3.13` 这一个版本**，所以不管建多少个 venv，全都会指向这唯一一份文件——这不是巧合，是"没有第二个选项"的必然结果。如果装了 `python@3.11` 再建一个基于它的 venv，那个 venv 的 `.venv/bin/python3.11` 就会是一个真正不同的物理文件，跟 steward 这份 `python@3.13` 不再相同——到那时候，维度二（版本隔离）才会真正体现出差异，现在只是维度一（包隔离）在起作用。
